Chapter 7 · A new performance-quality tradeoff

Downsampled blur

Question: Can we make the blur process fewer pixel positions?

Yes. First make a smaller working image. Blur that smaller image. Then enlarge the blurred result to the final output size.

New mechanism: shrink → blur → enlarge.
Tradeoff: fewer working pixels can reduce blur work, but small visual details may disappear before the image is enlarged.

1 · THE WHOLE IDEA

What “downsample” means here

1. Shrink

Downsample means create a smaller image by combining groups of source pixels. A 2 × 2 source block becomes one working pixel when width and height are both halved.

2. Blur

Run the blur on the smaller working image. The blur now produces fewer output pixel positions.

3. Enlarge

Upsample means enlarge the blurred working image back to the required display size.

Do not read “one quarter of the pixels” as “four times faster.” It is an area count. Real frame time also depends on the renderer, hardware, memory traffic, layer setup, and surrounding work.

4 · ONE DOWNSAMPLE CALCULATION

Four source pixels become one working pixel

This controlled arithmetic uses a 2 × 2 source block. It is separate from the larger interactive image.

P1
RGB(20, 40, 80)
P2
RGB(60, 80, 120)
P3
RGB(100, 120, 160)
P4
RGB(140, 160, 200)

These four pixels occupy one 2 × 2 block in the full-size source.

Average each channel

red = (20 + 60 + 100 + 140) ÷ 4 = 80 green = (40 + 80 + 120 + 160) ÷ 4 = 100 blue = (80 + 120 + 160 + 200) ÷ 4 = 140 one working pixel = RGB(80, 100, 140)

The working image now has one pixel where the full-size image had four.

Teaching boundary: this four-pixel average makes the information loss visible. The Android example does not manually average exact 2 × 2 blocks; it draws into a smaller layer, and Compose does not expose the renderer’s exact resizing filter here.
5 · SIZE AND RADIUS

Keep the arithmetic separate

Define the values first:

NameMeaningUnits
Wfinal output widthpixels
Hfinal output heightpixels
sworking-image scale applied to both width and heightratio from 0 to 1
Rdesired blur radius measured in final-output pixelspixels

Working pixel count

working width = W × s working height = H × s working pixels = (W × s) × (H × s)

Example with W = 320 and H = 160:

s = 1.00 → 320 × 160 = 51,200 pixels s = 0.50 → 160 × 80 = 12,800 pixels s = 0.25 → 80 × 40 = 3,200 pixels

Radius inside the smaller image

working radius = R × s

Example with desired final radius R = 24 px:

s = 1.00 → working radius = 24 px s = 0.50 → working radius = 12 px s = 0.25 → working radius = 6 px

At half size, one working-image pixel becomes two final-output pixels when enlarged. A 12-pixel working radius therefore spans roughly 24 final pixels after enlargement.

Evidence boundary: BlurEffect exposes radius values, but it does not expose Android's private sample count or weights. The scale calculation preserves the radius distance in output coordinates; it does not describe the internal blur kernel.

workingLayer.record(

    layoutDirection = layoutDirection,

    scale(
        scaleX = workingScale,
        scaleY = workingScale,
        pivot = Offset.Zero,

        drawLayer(sourceLayer)
    }
}

workingLayer.renderEffect = blurEffect

val enlargeScale = 1f / workingScale
workingLayer.pivotOffset = Offset.Zero
workingLayer.scaleX = enlargeScale
workingLayer.scaleY = enlargeScale

drawLayer(workingLayer)

What each part changes

size = IntSize(...) gives the working layer fewer pixel positions.

size = workingSize changes the recording target bounds; it does not resize sourceLayer by itself.

The inner DrawScope.scale(...) changes source-command coordinates so the full source fits those smaller bounds.

The blur radius is reduced by the same scale.

pivotOffset chooses the working-layer-local point that remains fixed while scaleX and scaleY enlarge the completed layer.

Full source: sourceLayer
Smaller blur target: workingLayer
Final destination: the current drawing target.

10 · EXPLAIN IT BACK
Eight checks

    
Why does half width and half height give one quarter of the pixel positions?
The width has factor 0.5 and the height has factor 0.5. Area uses both: 0.5 × 0.5 = 0.25.

    
Why reduce the blur radius inside the smaller image?
The smaller result will later be enlarged. At half size, one working pixel becomes two final pixels. Multiplying the radius by 0.5 keeps its final displayed distance roughly aligned with the requested full-size radius.

    
What quality can be lost?
Small dots, thin lines, narrow text strokes, and tiny color changes may be combined into larger working pixels before blur. Enlarging cannot recover details that were removed during shrinking.

    
Does one quarter of the pixel positions prove a four-times speedup?
No. It proves only the working target's pixel-position count. Device speed must be measured because other costs remain.

    
What does size = workingSize do by itself?
It defines the smaller layer size and the recording DrawScope.size. It does not automatically resize or select the source commands. In this code, the later RenderEffect forces rasterization into a buffer of that size, which is when transformed content outside the layer bounds is clipped.

    
How are the two pivots different?
The DrawScope.scale pivot changes source coordinates while the working layer is recorded. GraphicsLayer.pivotOffset changes how the completed working layer is transformed later when it is drawn.

    
Why use Offset.Zero for both production pivots?
The source, working layer, and output are intended to share local top-left coordinate (0, 0). Keeping that point fixed avoids transparent margins and corrective translations.

    
Why does my familiar center-scale picture differ from this code?
Your familiar picture keeps the 483 × 528 destination while scaling. Here, record(size = workingSize) first creates a smaller 242 × 264 recording coordinate space. A center pivot inside that lambda is therefore the center of the smaller working space, not the center of the original source.
