Chapter 7 · A new performance-quality tradeoff

Downsampled blur

Question: Can we make the blur process fewer pixel positions?

Yes. First make a smaller working image. Blur that smaller image. Then enlarge the blurred result to the final output size.

New mechanism: shrink → blur → enlarge.
Tradeoff: fewer working pixels can reduce blur work, but small visual details may disappear before the image is enlarged.

1 · THE WHOLE IDEA

What “downsample” means here

1. Shrink

Downsample means create a smaller image by combining groups of source pixels. A 2 × 2 source block becomes one working pixel when width and height are both halved.

2. Blur

Run the blur on the smaller working image. The blur now produces fewer output pixel positions.

3. Enlarge

Upsample means enlarge the blurred working image back to the required display size.

Do not read “one quarter of the pixels” as “four times faster.” It is an area count. Real frame time also depends on the renderer, hardware, memory traffic, layer setup, and surrounding work.

4 · ONE DOWNSAMPLE CALCULATION

Four source pixels become one working pixel

This controlled arithmetic uses a 2 × 2 source block. It is separate from the larger interactive image.

P1
RGB(20, 40, 80)
P2
RGB(60, 80, 120)
P3
RGB(100, 120, 160)
P4
RGB(140, 160, 200)

These four pixels occupy one 2 × 2 block in the full-size source.

Average each channel

red = (20 + 60 + 100 + 140) ÷ 4 = 80 green = (40 + 80 + 120 + 160) ÷ 4 = 100 blue = (80 + 120 + 160 + 200) ÷ 4 = 140 one working pixel = RGB(80, 100, 140)

The working image now has one pixel where the full-size image had four.

Teaching boundary: this four-pixel average makes the information loss visible. The iOS explorer does not manually average exact 2 × 2 blocks. It draws into a smaller bitmap. Core Image does not expose that draw’s resampling as this four-pixel average.

Working pixel count

working image width = final output width × working scale working image height = final output height × working scale working pixel count = working image width × working image height

Example values:

final output width = 320 px final output height = 160 px At full size: working image width = 320 × 1.00 = 320 px working image height = 160 × 1.00 = 160 px working pixel count = 320 × 160 = 51,200 At half width and half height: working image width = 320 × 0.50 = 160 px working image height = 160 × 0.50 = 80 px working pixel count = 160 × 80 = 12,800 At quarter width and quarter height: working image width = 320 × 0.25 = 80 px working image height = 160 × 0.25 = 40 px working pixel count = 80 × 40 = 3,200

Radius inside the smaller image

working-image blur radius = desired final blur radius × working scale

Example values:

desired final blur radius = 24 px At full size: working-image blur radius = 24 × 1.00 = 24 px At half width and half height: working-image blur radius = 24 × 0.50 = 12 px At quarter width and quarter height: working-image blur radius = 24 × 0.25 = 6 px

At half size, one working-image pixel occupies approximately two final-output pixels after enlargement. A 12-pixel working radius therefore occupies approximately 24 final-output pixels.

Evidence boundary: CIGaussianBlur exposes a pixel sigma, but it does not expose its sample count or weights. The scale calculation preserves the radius distance in output pixels. It does not describe the internal blur kernel. SwiftUI .blur(radius:) is not the call that blurs the smaller bitmap.
6 · iOS ROUTE

One smaller bitmap

let outputWidthPx = Int((size.width * displayScale).rounded())
let outputHeightPx = Int((size.height * displayScale).rounded())
let workingWidthPx = max(1, Int((CGFloat(outputWidthPx) * workingScale).rounded()))
let workingHeightPx = max(1, Int((CGFloat(outputHeightPx) * workingScale).rounded()))
let workingRadiusPx = finalRadiusPx * workingScale

let source = renderDownsampleSource(
    pixelWidth: outputWidthPx,
    pixelHeight: outputHeightPx,
    displayScale: displayScale
)
let working = drawScaled(
    source,
    pixelWidth: workingWidthPx,
    pixelHeight: workingHeightPx,
    scale: workingScale,
    pivot: recordingPivot
)
let blurred = blurClamped(working, sigma: workingRadiusPx)
let output = drawScaled(
    blurred,
    pixelWidth: outputWidthPx,
    pixelHeight: outputHeightPx,
    scale: 1 / workingScale,
    pivot: placementPivot
)

What each part changes

workingWidthPx and workingHeightPx give the working bitmap fewer pixel positions.

That smaller size is the destination of the first drawScaled. It does not resize source by itself.

recordingPivot is the point that stays fixed while workingScale maps the full source into the smaller bitmap. Top-left is .zero. Center is the center of the smaller bitmap, not the center of the original artwork.

workingRadiusPx is the final pixel radius multiplied by the same scale. blurClamped runs CIGaussianBlur on the smaller bitmap and repeats edge pixels outside that bitmap.

placementPivot is the point that stays fixed while 1 / workingScale enlarges the already-blurred bitmap into the output.

7 · TWO SCALES, FOUR CASES

Which original pixels are stored, and where do they land?

The iOS route uses two separate scales. First the full source is drawn into a smaller bitmap. Then that stored bitmap is enlarged onto the final output. Each scale has its own thumbtack: the point that stays put while everything else moves.

10 · EXPLAIN IT BACK

Eight checks

Why does half width and half height give one quarter of the pixel positions?

The width has factor 0.5 and the height has factor 0.5. Area uses both: 0.5 × 0.5 = 0.25.

Why reduce the blur radius inside the smaller image?

The smaller result will later be enlarged. At half size, one working pixel becomes two final pixels. Multiplying the radius by 0.5 keeps its final displayed distance roughly aligned with the requested full-size radius.

What quality can be lost?

Small dots, thin lines, narrow text strokes, and tiny color changes may be combined into larger working pixels before blur. Enlarging cannot recover details that were removed during shrinking.

Does one quarter of the pixel positions prove a four-times speedup?

No. It proves only the working target's pixel-position count. Device speed must be measured because other costs remain.

What does the smaller bitmap size do by itself?

It defines the smaller pixel grid. It does not automatically resize the source image. drawScaled maps source coordinates into that grid. Pixels that land outside the grid are not stored. blurClamped then blurs only the pixels that were stored.

How are the two pivots different?

The recording pivot chooses how the original artwork lands on the smaller bitmap. The placement pivot chooses where that already-stored bitmap lands on the final output. The second thumbtack cannot restore original pixels that the first photocopy discarded. Open the four scaling cases if this is still fuzzy.

Why use top-left for both production pivots?

Both thumbtacks stay at the working bitmap’s top-left (0, 0). The whole source then lands on the smaller bitmap, and that bitmap fills the output. Other thumbtack combinations crop or shift the image. Those four cases are in the companion, not in this page.

Why does a familiar center-scale picture differ from this code?

The familiar picture keeps the original destination and shrinks the artwork inside it. Here, the smaller bitmap is a new piece of paper. A “center” thumbtack is the center of that smaller paper, which is not the center of the original artwork.
