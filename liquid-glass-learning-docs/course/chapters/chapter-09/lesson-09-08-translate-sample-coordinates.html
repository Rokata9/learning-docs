Chapter 9 · Read a different pixel than you write

Translate sample coordinates

Question: Lesson 9.7’s eval(fragCoord) copies the input color at this pixel. The write location and the read coordinate are the same pair, so the stripes sit still. How do you paint this pixel with the color from a neighbor, so the background appears to slide?

Subtract a width-fraction offset from the read x before eval. The current pixel still stores the returned half4. Because the color came from the left, the stripes appear to have moved right. The picture shifts opposite the read offset.

Canonical wording: eval, read coordinate, sampled color.

Complete. Default offsetU = 0.10 is one stripe width as a fraction of the rectangle width. Teaching write uv.x = 0.15 then reads uv.x = 0.05 and stores orange. HTML is a JavaScript stand-in. Lesson 9.10 is the unresolved checkpoint.
1 · THE NEW QUESTION

The write location stays put. The read coordinate moves.

9.7 leftover

eval still returns the sampled color: a copy of the input half4 at the pair you pass. The stripe input is unchanged: fract(uv.x × 5.0).

offsetU

offsetU is how far left to read, as a fraction of the rectangle width. It uses the same 0..1 family as UV. Default 0.10 is one stripe width. On 400 px that is 40 px.

Read coordinate

The read coordinate is fragCoord − (offsetU × resolution.x, 0). Subtracting a positive x reads a pixel to the left. This pixel still stores the returned color, so the stripe that lived on the left is painted here.

readCoord = fragCoord − float2(offsetU × resolution.x, 0) sampled = background.eval(readCoord) return sampled
Teaching write W uv.x = 0.15 · x = 60 px offsetU = 0.10 · 40 px read uv.x = 0.15 − 0.10 = 0.05 cell = fract(0.25) = 0.25 → orange W stores orange. The input at 0.15 was navy.
2 · THE PICTURE MOVES THE OTHER WAY

Reading left paints that left color here, so the stripes appear to move right.

The input shader does not move. Only the pair passed to eval changes. A viewer looking at this shader’s store sees the orange band that used to start at the left edge now starting farther right. That is the opposite of the pink subtract arrow.

offsetU = 0.10 swaps every stripe

One stripe is 0.10 of the width. Reading one stripe width to the left maps each orange pixel onto a navy write location, and each navy pixel onto an orange write location. T flips from navy to orange.

offsetU = 0.20 looks like identity

0.20 is one full orange-navy pair. Each pixel reads a neighbor of the same color. The store matches offset 0. The input still did not move. You read two stripes over.

eval does not wrap the pair

A write pixel with x below 40 and offsetU = 0.10 asks eval at a negative x, for example 20 − 40 = −20. eval passes that pair as written. It does not map −20 to 380. The stripe input still returns a color because its own fract(uv.x × 5.0) is defined for every uv.x. At uv.x = −0.05, cell = fract(−0.25) = 0.75, navy. That leftover wrap is Lesson 8.10. Wrapping a bitmap pixel is Lesson 9.12.

positive offsetU → read x is smaller → color comes from the left → picture appears shifted right negative offsetU → read x is larger → color comes from the right → picture appears shifted left write x = 20, offsetU = 0.10 → read x = 20 − 40 = −20 → eval(−20, y), not eval(380, y)

5 · ANDROID ROUTE
One new uniform: offsetU. eval still receives pixels.

    

      
private const val DefaultOffsetU = 0.10f
private const val TeachU = 0.15f

uniform shader background;
uniform float2 resolution;
uniform float offsetU;

half4 main(float2 fragCoord) {
    float2 readCoord = fragCoord - float2(offsetU * resolution.x, 0.0);
    return background.eval(readCoord);
}

      

        
What each part changes

        
offsetU is a width fraction, not a pixel count, so a 360 dp panel and a 400 px HTML square shift by the same stripe amount.

        
offsetU * resolution.x converts that fraction into pixels because eval still wants the Lesson 8.4 unit. A negative result stays negative. eval does not wrap it into the rectangle.

        
The slider writes offsetU. It does not rebuild the program. Default 0.10 so T’s store is orange on first draw.

        
The stripe input is the same 9.7 program. Geometry masks are unused. A y subtract would be the same idea on the second member; this lesson keeps y at 0.

8 · EXERCISES
Answer before opening each hidden solution

    
At offsetU = 0, what is readCoord, and what color does W store?
readCoord = fragCoord. Identity, same as Lesson 9.7 without the split. W’s uv.x = 0.15 still samples navy.

    
Diagnostic: someone writes eval(fragCoord + float2(offsetU * resolution.x, 0)) with offsetU = 0.10. T still stores orange. What did they get wrong?
Adding reads to the right. One stripe width still lands on the opposite color at T, so T’s store is orange either way. The field is the proof: colors from the right are painted here, so the stripes appear shifted left. Subtract reads left and the picture appears shifted right.

    
At offsetU = 0.20, why does the store look like offset 0?
0.20 is one full orange-navy pair. W reads uv.x = −0.05. eval still asks the input at that negative pair. The input’s repeating fract treats −0.05 as the same stripe color as 0.15: fract(−0.25) = 0.75, navy. Every pixel reads a neighbor two stripes over of the same color. The input did not move. eval did not wrap −20 to 380.

    
Does this lesson move the Canvas or change p?
No. The draw rectangle stays put. p is unused. Only the pair passed to eval changes. Lesson 9.9 will scale around the center using p.

10 · EVIDENCE BOUNDARY
What this lesson establishes

    

      
Established
The read coordinate can differ from the write location. readCoord = fragCoord − (offsetU × width, 0). Default offsetU = 0.10. Teaching write uv.x = 0.15 reads 0.05 and stores orange. The picture appears to shift opposite the read offset. Production returns the sampled color at every pixel. eval does not wrap a negative read x. The stripe input’s fract still returns a color.

      
What’s next
Lesson 9.9 will scale around the center using p: magnification and minification of the same input. A later displacement field (9.10) will make the offset itself vary by pixel. Edge reads past the rectangle are Lesson 9.12. A bitmap input would not keep striping past the edge unless its tile mode wrapped.
