Chapter 9 · The inner rectangle is the image of the square under a halved walk

Scale around the center

Hard question: The yellow rectangle on the input is the middle 2 × 2. The store is that same rectangle, stretched. The shader never tests “am I in the inner half?” How does halving every walk from C pick exactly those sub-bounds, what color each halved walk lands on, and where the outer ring would be painted?

No if. Every write halves its walk from C. The store is four big squares: the inner 2 × 2, each cell copied onto many writes, not averaged. Outer input would be painted off-picture. On the diagonal (0,0) → (1,1), half the walk is the inner-rect corner (0.75, 0.75), still orange.

Canonical wording: scale around the center, read coordinate, eval.

1 · THE INNER RECTANGLE, DRAWN

No if. The window is whatever the edge writes ask.

Leftover, one card: W stays. Scale 2 asks a neighbor half as far from C on the same ray. Copy that color onto W.

4 × 4 cells

Each cell is 0.25 of the square. That is why the inner-rect edge at 0.25 from C sits on a cell border, and why the inner rectangle is a clean middle 2 × 2.

Inner rectangle

From 0.25 to 0.75 on each axis. That is 0.25 from C left, right, up, and down. Yellow stroke. The outer ring is dimmed because no in-square write will ask it.

No membership test

The Metal function is p / scale + 0.5 at every pixel. There is no if for the inner half. The inner rectangle is the image of the square under “halve the walk.”

Start at C. The ask is 0. Walk W toward an edge. The ask walks the same ray at half speed. When W hits the right edge, it is 0.50 from C, so the ask is 0.25 from C — the inner rectangle’s right side. Left, top, and bottom match. The four corners of the square map to the four corners of the inner rectangle. Every write closer than an edge asks closer than 0.25 on that axis, so it is still inside. That is the whole window. Your guess was right: we move from the center out, and “half” at the edge is exactly this teaching inner half.

right-edge write: 0.50 from C → ask 0.25 from C (inner-rect right side) left-edge write: 0.50 left → ask 0.25 left corner write (1, 1): walk (0.50, 0.50) → ask (0.25, 0.25) from C that ask is UV (0.75, 0.75), the inner-rect corner closer writes ask closer than that → still inside no if

2 · THE FOUR STORE SQUARES

After scale 2 the store is four big squares. Each is one inner cell, copied.

Look at the store, not at a coded flip. The inner 2 × 2 becomes four big squares that fill the picture:

Store top-left

Copies the inner top-left input cell. Orange.

Store top-right

Copies the inner top-right input cell. Navy.

Store bottom-left

Copies the inner bottom-left input cell. Navy.

Store bottom-right

Copies the inner bottom-right input cell. Orange.

A write in the store’s right half sits in the two right squares. It copies the inner-right input cell, not the outer-right input cell that used to sit at that seat. A write in the store’s left half copies the inner-left input cell. That is the whole color story. No “navy-right → orange” code.

The strip below is the middle row of that picture. Pick a distance. Pink is W. Green is half that walk, which lands in one of those four inner cells.

2b · MANY WRITES, ONE INPUT CELL

Scale 2 still evals once per write. Neighboring writes copy the same cell. No average.

We do not sample fewer times. Every write pixel still calls eval once — the same number of asks as identity. Those asks all point into the inner half of the input, which is half the width and half the height. So several neighboring writes land in one input cell and get the same color. That is why each inner cell becomes a big square.

Same cell, many writes

Four neighboring writes in the store’s bottom-right square can all ask inside the inner bottom-right cell. All four store orange. Two writes can share one read cell. At scale 2, about four writes share one input pixel in each axis-pair (2 × 2).

Not bilinear scaling

Image scaling that “adds pixels” often averages neighbors (bilinear: a new pixel is a blend of four). This shader does not blend. eval of the checker returns that cell’s color exactly. A whole block is identical orange or navy. No new mixed color.

Not “half as many samples”

Half the input area is asked. The number of samples is still one per write pixel. The asks are packed denser on that inner rectangle.

Four neighboring write pixels, one input cell

Take the 2 × 2 block of write pixels at the top-left of the store: (0, 0), (1, 0), (0, 1), (1, 1). Those are pixel seats, not UV corners of the square. The lab is 400 × 400, so one pixel is 1/400 of the width. Scale 2 uses readUv = uv / 2 + 0.25.

readUv = write pixel / 800 + 0.25 eval pixels = readUv × 400 = write pixel / 2 + 100 (0, 0) → UV (0.25000, 0.25000) → eval (100.0, 100.0) px (1, 0) → UV (0.25125, 0.25000) → eval (100.5, 100.0) px (0, 1) → UV (0.25000, 0.25125) → eval (100.0, 100.5) px (1, 1) → UV (0.25125, 0.25125) → eval (100.5, 100.5) px

The four asks are not the same pair. Write (1, 0) asks 100.5 pixels from the left. That is half a pixel past 100. They do not get rounded to one store pixel, and they do not get rounded to one read pixel.

The store is still discrete

Lesson 2.1: one output pixel is one addressable seat. We write four different pixels: (0,0), (1,0), (0,1), (1,1). You cannot display half a pixel. Each of those four seats stores a whole color.

The ask is a float pair

eval of this checker is a function: any pixel pair in, a color out. Lesson 8.6 already used fragCoord.x = 399.5. Lesson 2.8 already put a pixel center at 7.5. The pair passed to eval can sit between whole numbers. The input shader does not snap 100.5 to 100 before it runs.

Same orange because they sit in the same cell, not because they snapped to the same pixel. The inner top-left cell is UV [0.25, 0.50), which is pixels [100, 200) — one hundred pixels wide. 100.0 and 100.5 are both inside that bar. The checker computes floor(uv × 4) at the exact float. floor(1.000) = 1 and floor(1.005) = 1, so both return orange.

If the input were a bitmap, a filter might snap 100.5 to a neighboring texel or blend two texels. This input is a shader. No snap. Filtering a bitmap is later.

The same packing happens away from the corner. Write pixels (320, 320), (321, 320), (320, 321), (321, 321) are a 2 × 2 in the store’s bottom-right square. They ask (0.65000, 0.65000), (0.65125, 0.65000), (0.65000, 0.65125), (0.65125, 0.65125). All four sit in the inner bottom-right cell [0.50, 0.75) × [0.50, 0.75), so all four store orange.

3 · FORTY-FIVE DEGREES

Half of C → (1,1) is (0.75, 0.75). Inner-rect corner. Not orange/navy on this diagonal.

Walk the diagonal of the square from (0, 0) to (1, 1). C is the midpoint (0.50, 0.50). The walk from C to the bottom-right corner is 0.50 right and 0.50 down. Half of that walk is 0.25 right and 0.25 down.

(0, 0) -------- C -------- (1, 1) C = midpoint C → (1, 1) = (0.50, 0.50) half = (0.25, 0.25) from C ask UV = (0.75, 0.75) inner-rect corner

Is that the orange/navy border? On this diagonal, column equals row, so column + row is even, so every cell on y = x is orange. Inner diagonal cell orange. Outer corner cell orange. Half the walk hits a cell-grid corner that does not change color. The orange/navy border is the axis-aligned cell edge at 0.25 from C, which you cross only when the walk is perpendicular to an axis. Halving still lands on the inner rectangle. It does not have to flip color.

4 · OUTSIDE THE INNER RECTANGLE

In-square writes never ask outside. Outer input would be painted off-picture.

Two different objects. Do not mix them.

Forward · what the shader does

A write in the outer ring of the store (0.30 from C, navy on the right) still just halves. The ask is 0.15 from C, inside the inner rectangle. No negative read. No ask past 0.25 from C. Scale 2, W inside the square: the ask is always inside the yellow rectangle.

Inverse · why the outer ring vanishes

Take an input point outside the inner rectangle, 0.40 from C. The inverse of divide-by-2 is multiply-by-2. That point would be painted 0.80 from C. The square only goes to 0.50 from C. Right side: UV 1.30, past the right edge. Left side: UV −0.30, off-picture to the left. Those colors never appear in the store. The formula did not go negative on a read. The missing outer ring is a write that would sit outside the picture.

forward, W 0.40 from C: ask 0.20 from C · still inside the inner rect inverse, input 0.40 right of C: painted at 0.80 from C · UV 1.30 · off-picture inverse, input 0.40 left of C: painted at 0.80 left · UV −0.30 · negative, off-picture

When scale is 0.50 the forward ask itself walks past the edge (teaching 0.30 becomes 0.60 from C). That gray band in the lab is a read outside the picture. Lesson 9.12. It is not the inner-rect story at scale 2.

6 · iOS ROUTE
One new argument: scale. No inner-half if.

    

      
private let defaultScale: Double = 2.00
private let teachU: Double = 0.80
private let teachV: Double = 0.50
private let panelSizePt: CGFloat = 360

[[ stitchable ]] half4 scaleAroundCenter(
    float2 position,
    half4 color,
    float2 resolution,
    float displayScale,
    float scale
) {
    float2 fragCoord = position * displayScale;
    float2 uv = fragCoord / resolution;
    float2 p = uv - float2(0.5, 0.5);
    float2 readUv = p / scale + 0.5;
    return background(readUv * resolution, resolution);
}

ShaderRect(
    shader: ShaderLibrary.scaleAroundCenter(
        .float2(pixelWidth, pixelHeight),
        .float(Float(displayScale)),
        .float(Float(scale))
    )
)
.frame(width: panelSizePt, height: panelSizePt)

      

        
What each part does

        
p is this pixel measured from C. The leftover − 0.5 and + 0.5 convert between UV and that walk. They are not the new idea.

        
p / scale is the walk. scale is the magnification, not displayScale. Default 2 asks a neighbor half as far from C. The inner rectangle is that window: edge 0.50 / 2 = 0.25 from C. There is no if.

        
The checker is four cells across so each cell is 0.25, matching the inner-rect edge. Orange when column plus row is even. background is that checker in ScaleAroundCenter.metal. It is not the Lesson 9.7 stripe function, and it is not a texture sample.

        
position is points, so fragCoord = position * displayScale. pixelWidth and pixelHeight are 360 × displayScale. resolution is that pixel size. The slider writes scale with .float. It does not rewrite the .metal file. Pass every argument. Leaving one out still compiles the Swift file, and SwiftUI refuses that draw.

        
At scale 0.50 a read can leave the picture. The call does not clamp it. The HTML lab paints that outside read gray. The Metal function still calls background. Lesson 9.12 owns the edge.

9 · EXERCISES
Answer before opening each hidden solution

    

      A write in the store’s bottom-right square: what input cell does it copy, and do neighboring writes in that same square get the same color?
      
It copies the inner bottom-right input cell, which is orange. Neighboring writes in that square also ask inside that same inner cell, so they store the same orange. Many writes, one cell. No average.

    

    

      Name the four store squares and their colors after scale 2.
      
Top-left orange, top-right navy, bottom-left navy, bottom-right orange. Those are the inner 2 × 2, each cell twice as wide and twice as tall. The outer ring of the input is gone.

    

    

      Walk (0,0) → (1,1). What is half of C → (1,1)? Is that an orange/navy border?
      
Half of (0.50, 0.50) is (0.25, 0.25) from C, UV (0.75, 0.75), the inner-rect corner. On this diagonal column equals row, so every cell is orange. It is a grid corner, not an orange/navy border. The orange/navy border is the axis-aligned cell edge at 0.25 from C.

    

    

      An input point 0.40 left of C is outside the inner rectangle. Where would it be painted, and why is that not a negative read at scale 2?
      
Inverse of divide-by-2 is multiply-by-2: painted 0.80 left of C, UV −0.30, off-picture. In-square writes at scale 2 never ask that point. Their asks stay inside the inner rectangle. The negative number is a write that would sit left of the store, not a read the shader performs.
