Chapter 9 · The write pixel stays. The walk from C gets shorter.

Scale around the center

Question: Lesson 9.8 subtracted the same width-fraction at every write pixel. The whole stripe picture slid, including the visual center. How do you keep the pixel at C copying itself, while a far pixel reads a neighbor closer to C, so the middle of the input looks larger?

The write pixel does not move. Subtract 0.5 only to number that same pixel from C. Divide that walk so the ask is closer to C. Add 0.5 to name that neighbor in UV. eval needs a top-left pair. Adding 0.5 is the inverse of the subtract. Nobody relocates.

Canonical wording: scale around the center, read coordinate, eval, origin of a pair.

Unresolved checkpoint. Lesson 9.8 is complete. Default scale = 2 means “twice as large,” so the walk from C is half as long. Teaching write uv = (0.80, 0.70) is 0.30 right of C and 0.20 below it. HTML is a JavaScript stand-in. Lesson 8.8’s × 2 is unused.
1 · THE WRITE PIXEL DOES NOT MOVE

W still stores here. R is a different pixel we ask.

Lesson 9.8 already split two jobs. The write location is this pixel: it stores the returned half4. The read coordinate is the pair passed to eval: the input color we copy. Those can be different pixels. The write pixel does not slide onto the read pixel. The input picture does not move. Canvas does not scale.

2 · TWO NAMES FOR THE SAME PIXEL

Subtract 0.5 is a rename, not a slide.

uv.x = 0.80 means: 0.80 of the width from the left. That is Lesson 8.6. C sits at 0.50 because it is the middle of 0..1. The extra pair from Lesson 8.8 is p = uv − 0.5. For this write pixel:

p.x = uv.x − 0.5 = 0.80 − 0.50 = 0.30

0.80 and 0.30 are two names for one pixel. 0.30 is “this far right of C.” The pixel did not jump 0.50 toward the left. The second ruler only changes which 0 we measure from.

Why 0.80, not a random teaching x. It is 0.30 of the width right of C. 0.30 is a clean half-of-something once we shorten the walk. The 2D pair (0.80, 0.70) is that x and the matching y 0.20 below C. Both members use the same three operations.
3 · WHY THE DIVIDE EXISTS

scale = 2 means twice as large, so the walk is half as long.

The slash is not a decoration on a 2. We first choose a stored picture: the inner half of the input should fill the whole square. That stored picture looks twice as large. The number of that choice is scale = 2.

The proof is the right-edge write, not the teaching pixel. A write at the right edge has uv.x = 1, so p.x = 1 − 0.5 = +0.5. For the inner half to reach that edge, that write must read the right edge of the inner half, which is UV 0.75, whose p name is +0.25.

right-edge write p.x = uv.x − 0.5 = 1.00 − 0.50 = +0.50 we want readP.x = +0.25 ← right edge of the inner half +0.50 / 2 = +0.25 readUv.x = readP.x + 0.5 = 0.25 + 0.50 = 0.75

Left-edge write is the mirror: p.x = −0.5, −0.5 / 2 = −0.25, UV 0.25. So every store pixel reads some UV in 0.25..0.75. That band stretches across 0..1. That is magnification by 2.

The teaching write then uses the same shorten, not a second recipe. Its walk from C is 0.30. Half of that walk is 0.15. The green tick in the hero is that half.

teaching write W, x only p.x = uv.x − 0.5 = 0.80 − 0.50 = 0.30 readP.x = p.x / scale = 0.30 / 2.00 = 0.15 W is still at UV 0.80. R is a different pixel, 0.15 right of C.

scale > 1

Walk a shorter input distance. Cells look larger. Magnification. Default 2.00.

scale = 1

Walk the same distance. readP = p. Identity. W reads W.

scale < 1

Walk a longer input distance. Cells look smaller. Minification. Edge writes can ask past 0..1. That edge is Lesson 9.12. The lab paints those asks gray.

Lesson 8.8’s × 2 is unused. That multiply made 1 mean one half-width so an if could test p. This lesson never tests p with an if. It shortens the walk, then converts back to UV for eval. After × 2, the right edge would be +1 and you would have to divide by a different number to hit +0.25. Staying in −0.5..+0.5 keeps the divide equal to the enlargement we chose.
4 · WHY ADD 0.5

0.15 is a p-name. eval does not speak p.

readP.x = 0.15 is how far R sits from C. eval wants pixels from the top-left of the draw rectangle, the Lesson 8.4 unit. Those pixels are UV × resolution. So R still needs a UV name.

Look at the hero’s dashed green line. The p-tick 0.15 sits on the same physical mark as the UV-tick 0.65. Adding 0.5 reads that UV name:

readUv.x = readP.x + 0.5 = 0.15 + 0.50 = 0.65 readCoord.x = readUv.x × resolution.x

Adding 0.5 is the inverse of the subtract that built p. It does not move R. It names R in the family eval consumes after the × resolution convert.

x p.x = 0.80 − 0.50 = 0.30 readP.x = 0.30 / 2.00 = 0.15 readUv.x = 0.15 + 0.50 = 0.65
y, same operations p.y = 0.70 − 0.50 = 0.20 readP.y = 0.20 / 2.00 = 0.10 readUv.y = 0.10 + 0.50 = 0.60

6 · ANDROID ROUTE
One new uniform: scale. eval still receives pixels.

    

      
private const val DefaultScale = 2.00f
private const val TeachU = 0.80f
private const val TeachV = 0.70f

uniform shader background;
uniform float2 resolution;
uniform float scale;

half4 main(float2 fragCoord) {
    float2 uv = fragCoord / resolution;
    float2 p = uv - float2(0.5, 0.5);
    float2 readUv = p / scale + 0.5;
    return background.eval(readUv * resolution);
}

      

        
What each part changes

        
p = uv - 0.5 names this write pixel from C. The pixel does not move.

        
p / scale shortens that walk. Default 2 is “twice as large,” so the walk is half as long. The right-edge proof is 0.5 / 2 = 0.25.

        
+ 0.5 is the UV name of that neighbor. eval does not speak p.

        
readUv * resolution is the Lesson 8.4 unit eval still wants.

        
The checker input is four cells across. Column floor(uv.x × 4.0). Orange when that column plus the row is even. Geometry masks are unused.

        
Lesson 9.8’s subtract was the same pixel count at every write. This divide is 0 at C and larger farther out, so C still copies C.

9 · EXERCISES
Answer before opening each hidden solution

    

      At scale = 1, what is readUv at W, and what color does W store?
      
readP = p / 1 = p, so readUv = p + 0.5 = uv. Identity. W’s input cell is navy, so W stores navy. R sits on W.

    

    

      Why divide the right-edge write by 2, instead of by some other number, when we want the inner half to fill the square?
      
The right-edge write has p.x = +0.5. The right edge of the inner half has p.x = +0.25. The unique number that turns +0.5 into +0.25 is 2. That 2 is the enlargement we chose: twice as large means the walk is half as long. The teaching 0.30 / 2 = 0.15 is the same shorten, not a different rule.

      
    

    

      Diagnostic: someone writes readUv = uv / scale with scale = 2. W can still store orange. What did they get wrong?
      
They skipped p = uv − 0.5. Dividing UV from the top-left thumbtacks (0, 0), not C. At C, uv / 2 = (0.25, 0.25), so the visual center copies a top-left cell. W can land on orange by accident. The field is the proof: C no longer copies C.

    

    

      If you divide p by 2 and skip + 0.5, what UV does W ask, and why is that the wrong neighbor?
      
You would pass readP = (0.15, 0.10) as if it were UV. UV 0.15 is near the left edge, a different physical tick from p 0.15. p 0.15 lines up with UV 0.65. Skipping the add asks the left, not the neighbor of C.

    

    

      At scale = 0.50, W has uv = (0.80, 0.70). What is readUv, and why can the store be gray?
      
readP = p / scale = (0.30, 0.20) / 0.50 = (0.60, 0.40). readUv = readP + 0.5 = (1.10, 0.90). The 1.10 is past the right edge. This HTML stand-in stores gray for any read UV outside 0..1. Android’s eval of an out-of-range pair is Lesson 9.12. Minification is still “walk farther on the input.” W still sits at (0.80, 0.70).
