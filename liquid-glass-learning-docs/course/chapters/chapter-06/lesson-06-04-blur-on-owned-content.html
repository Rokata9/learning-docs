Chapter 6 · How SwiftUI draws the scene

Lesson 6.4 — .blur() on owned content

Lesson 6.3 grouped one owner's drawing instructions into an owner transform group. This lesson attaches .blur() to that owner and traces exactly which pixels enter the effect.

Practical problem: soften the card's own fill, stripe, dot, and label together while keeping the separately owned backdrop sibling sharp.

The boundary this lesson proves

.blur() input = pixels rasterized from the selected owner .blur() input ≠ automatic pixels from unrelated siblings behind it

Backdrop blur remains the subject of Lessons 6.5–6.8.

0 · PREREQUISITE LEDGER

Name every object before the effect runs

Only the owned-blur modifier is new.

Backdrop sibling

A separately owned pattern already drawn in the parent scene.

Effect owner

The OwnedCard view containing the blue fill, amber stripe, green dot, white detail lines, and label.

Owner view

The view whose rasterized pixels .blur() reads. Attachment point decides this boundary.

.blur()

A SwiftUI modifier applied to the pixels produced by one selected view before that view is composited into its destination.

Blur radius

The radius argument to .blur(radius:opaque:), measured in points. The averaging details are deferred to Chapter 7.

1 · ALL FORMULAS AND CONTRACTS

Keep the complete value path visible

The lesson does not reveal hidden blur weights.

iOS radius is in points

.blur(radius:) radius is in points controlled teaching value: r_pt = 12 pt displayScale is not a blur input

On iPhone 16 Pro, displayScale is typically 3, so 12 pt occupies 36 device pixels of screen size. That conversion is display geometry. It is not the argument type of .blur(). This lesson does not claim identical kernel weights to any other blur implementation.

Effect pipeline contract

owned draw commands → rasterize owner into pixels → .blur() reads those owner pixels → blurred owner output → source-over parent scene

The browser uses an SVG blur as a visual model. It does not claim identical internal weights or radius semantics.

Deferred mathematics: Chapter 7.1 teaches blur as neighborhood averaging. Lesson 6.4 teaches the ownership and data-route boundary first.

5 · iOS VALUE PATH

Pass a point radius and attach .blur() to the intended owner

Whole-owner attachment

let ownerBlur: CGFloat = blurRadiusPt

OwnedCardContent()
    .frame(width: 300, height: 190)
    .blur(radius: ownerBlur, opaque: false)

Why the parent is not the owner

ZStack {
    BackdropSibling()
    OwnedCard()
        .blur(radius: ownerBlur, opaque: false)
}

Attaching .blur() to the parent ZStack would make both siblings part of one effect input.

Fixed edge input: this lesson uses .blur(radius:opaque:) with opaque: false, which lets the blur mix with transparent pixels around the selected view. That is the closest SwiftUI analog to a transparent-outside edge. It is not a 1:1 kernel match. Detailed edge-treatment comparison is deferred to Lesson 7.3.
iOS explorer defaults: radius 12 pt, range 0...24, presets 0 / 6 / 12 / 22 pt. The browser slider below uses separate visual teaching units. displayScale is shown in the explorer only to prove it is not a blur input.

8 · EXERCISES

Check the ownership boundary

Exercise 1 · Label behavior

The effect is attached to the complete owner. Does the owned label stay sharp?

Show answer

No. The label belongs to the same owner input, so it is rasterized and blurred with the other owner content.

Exercise 2 · Dot-only attachment

The effect moves from the owner to the green-dot child. Which objects blur?

Show answer

Only the green-dot child. The base, stripe, detail lines, label, and backdrop remain outside that child effect input.

Exercise 3 · Pixel input

Owner opacity is 1, but .blur(radius:) is greater than 0. Does the blur still need the selected view as pixels?

Show answer

Yes. .blur() reads the selected view's rasterized pixels before compositing. That is a different claim from calling drawingGroup() yourself. This lesson does not call drawingGroup(). Lesson 6.10 measures extra render targets.

Exercise 4 · Backdrop blur

Why is this lesson not yet a real frosted-glass backdrop blur?

Show answer

The effect input contains owned card pixels, not a recorded image of the backdrop sibling. Later lessons create an explicit backdrop record, map the card region, and replay or read those pixels.

10 · SOURCES AND EVIDENCE

Primary iOS contracts used by the lesson

  • View.blur(radius:opaque:) — blurs the selected view's own pixels. This lesson does not use system materials as the glass path.
  • View.compositingGroup() — flattens a view for later compositing. Lesson 6.3 used it for whole-owner opacity.
  • View.drawingGroup(opaque:colorMode:) — explicit offscreen image. This lesson does not call it.
Evidence boundary: the browser reproduces ownership with an SVG blur. The iOS explorer executes real .blur(). It does not inspect the renderer's internal command stream, GPU allocations, or blur kernel weights, and it does not prove that drawingGroup() ran. .blur() kernels are not claimed to match any other platform's blur.
