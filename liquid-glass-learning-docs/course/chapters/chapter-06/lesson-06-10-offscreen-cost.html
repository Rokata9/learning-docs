Offscreen cost

A replayed backdrop can be visually correct and still cost more work than the frame budget allows. This lesson gives one panel-sized target a transparent, beginner-readable cost model—without pretending that an estimate is a profiler measurement.

First correction: the Lesson 6.9 controlled scene now uses one position value for both panel placement and crop translation. That removes the post-layout crop-state round trip that could make the sample trail the latest panel position.

Two symptoms that must not be confused

Alignment trail: the panel reaches a new position while its sampled crop still represents an older position. This is a synchronization or state-flow defect.

Frame stutter: the whole result misses a display deadline because the frame contains too much CPU or GPU work. This is a performance defect.

A faster phone may hide some expensive work. It cannot make mismatched geometry values become the same value.

1 · Practical problem

What extra target are we paying for?

Start with visible objects, not byte formulas.

Already owned: backgroundLayer

It stores replayable drawing work for BackdropArtwork. It lets another target ask Android to execute those commands again.

Important: this recording is not automatically the panel-sized color buffer that we estimate below.

New: panelSampleLayer

Its recording happens inside the panel’s draw scope. Its bounds therefore match the panel, and CompositingStrategy.Offscreen explicitly asks for an offscreen raster target.

The target receives only the matching sharp backdrop crop in this lesson. Blur remains deferred.

Offscreen target

A temporary image-shaped destination that is not yet the final screen output.

Rasterize

Execute drawing commands so they produce color samples in a pixel grid.

Target extent

The width and height of the pixel grid. A larger extent means more pixel positions.

Frame budget

The time between display updates: about 16.67 ms at 60 Hz or 8.33 ms at 120 Hz.

Measurement

A trace from the real app and device. Our arithmetic estimates scale; it does not report real GPU time.

Why this fixes the visible trail in the controlled scene

panelLeftDp controls both the layout offset and the negative source translation. There is no separately stored crop rectangle waiting for onGloballyPositioned to update after layout.

This simplification is valid here because BackdropHost fills ParentScene and both start at local origin (0, 0).

B · Make the raster target explicit

val panelSampleLayer = rememberGraphicsLayer()
panelSampleLayer.compositingStrategy =
    CompositingStrategy.Offscreen

panelSampleLayer.record {
    clipRect {
        translate(
            left = -cropLeftPx,
            top = -cropTopPx,
        ) {
            drawLayer(backgroundLayer)
        }
    }
}

drawLayer(panelSampleLayer)

Read the order literally

Record: execute the matching source replay in the panel-sized layer scope.

Raster target: Offscreen forces intermediate compositing.

Replay: draw the resulting layer into the panel before tint, child content, and border.

No full-scene comparison layer exists in the Android code.

9 · Explain it back

Five checks for the main idea

Open only after making your own explanation.

1 · Why is backgroundLayer not called the panel’s offscreen color target?

It holds replayable backdrop drawing work. The explicit panel-sized raster target in this lesson is panelSampleLayer, forced by CompositingStrategy.Offscreen.

2 · Why does panel movement not change estimated target bytes?

Movement changes the crop origin, but the target width, height, density, and bytes-per-pixel assumption remain unchanged.

3 · Why does doubling density approximately quadruple pixel count?

Both pixel width and pixel height double. Their product becomes 2 × 2 = 4 times the original pixel count.

4 · Why is 8.33 ms not “the blur’s available GPU time”?

It is the complete interval at 120 Hz. CPU work, layout, drawing, GPU work, synchronization, other app work, and system work share that interval.

5 · Why can a sample trail even when the byte estimate is small?

A trail can come from using panel geometry from one update and crop geometry from another. That is a correctness/synchronization defect, not necessarily excessive pixel work.

12 · Evidence boundary and local record

What this lesson proves—and what it does not

Generated is not the same as learner-confirmed complete.

Proved in this lesson

A panel-sized target has fewer pixel positions than a scene-sized target. Its simple RGBA8 storage estimate scales with pixel width × pixel height. The corrected controlled route uses one position source for placement and crop.

Still not proved

No exact GPU allocation, memory bandwidth, render time, blur cost, or dropped-frame count is claimed. Blur, downsampling, multi-panel architecture, and measured profiling remain later work.
