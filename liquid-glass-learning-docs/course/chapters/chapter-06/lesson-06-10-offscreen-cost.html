Chapter 6 · How SwiftUI draws the scene

Offscreen cost

A replayed backdrop can be visually correct and still cost more work than the frame budget allows. This lesson gives one panel-sized target a transparent, beginner-readable cost model—without pretending that an estimate is a profiler measurement.

Carried forward from Lesson 6.9: one panelLeft value places GlassPanel and supplies the negative crop offset. There is no second stored crop rectangle that can trail the panel.

Two symptoms that must not be confused

Alignment trail: the panel reaches a new position while its sampled crop still represents an older position. This is a synchronization or state-flow defect.

Frame stutter: the whole result misses a display deadline because the frame contains too much CPU or GPU work. This is a performance defect.

A faster phone may hide some expensive work. It cannot make mismatched geometry values become the same value.

1 · Practical problem

What extra target are we paying for?

Start with visible objects, not byte formulas.

Already owned: recordedBackdrop

ImageRenderer snapshots BackdropArtwork into an Image. Lessons 6.6–6.9 replay that image. On iOS the snapshot is pixels: the backdrop’s point size times displayScale.

Important: that source image is not the panel-sized color target estimated below. The panel estimate does not include it.

New: drawingGroup()

The cropped replay is a 196 × 116 pt view. drawingGroup(opaque: false) composites that view into one offscreen image before the tint, label, and border. The image extent matches the panel, so the arithmetic has one concrete target.

That call is a teaching choice. It does not improve the sharp replay and is not a general optimization. Blur remains deferred.

Offscreen target

A temporary image-shaped destination that is not yet the final screen output.

Rasterize

Execute drawing commands so they produce color samples in a pixel grid.

Target extent

The width and height of the pixel grid. A larger extent means more pixel positions.

Frame budget

The time between display updates: about 16.67 ms at 60 Hz or 8.33 ms at 120 Hz.

Measurement

A trace from the real app and device. Our arithmetic estimates scale; it does not report real GPU time.

Why the controlled scene does not trail

panelLeft controls both the layout offset and the negative source offset. There is no separately stored crop rectangle.

This is valid here because BackdropHost fills ParentScene and both start at local origin (0, 0). .offset uses points. Snapshot pixels are pt × displayScale and are not passed to .offset.

}

Read the order literally

Snapshot: ImageRenderer stores BackdropArtwork only. GlassPanel is not in that view.

Raster target: drawingGroup(opaque: false) forces one panel-sized offscreen image. The sharp picture would still align without it.

After the target: tint, label, and border draw on GlassPanel and stay outside that image.

No scene-sized drawingGroup() exists in the Swift file. Do not use ultraThinMaterial or glassEffect as the glass path.

Official reference: View.drawingGroup(opaque:colorMode:) composites the panel replay into an offscreen image. ImageRenderer snapshots BackdropArtwork. displayScale is the pixels-per-point value in the estimate.

9 · Explain it back

Five checks for the main idea

Open only after making your own explanation.

1 · Why is recordedBackdrop not called the panel’s offscreen color target?

It is the ImageRenderer image of the full backdrop. The explicit panel-sized raster target in this lesson is drawingGroup(opaque: false) on the 196 × 116 pt replay.

2 · Why does panel movement not change estimated target bytes?

Movement changes the crop origin, but the target width, height, displayScale, and bytes-per-pixel assumption remain unchanged.

3 · Why does doubling displayScale approximately quadruple pixel count?

Both pixel width and pixel height double. Their product becomes 2 × 2 = 4 times the original pixel count.

4 · Why is 8.33 ms not “the blur’s available GPU time”?

It is the complete interval at 120 Hz. CPU work, layout, drawing, GPU work, synchronization, other app work, and system work share that interval.

5 · Why can a sample trail even when the byte estimate is small?

A trail can come from using panel geometry from one update and crop geometry from another. That is a correctness or synchronization defect, not necessarily excessive pixel work.

12 · Evidence boundary and local record

What this lesson proves—and what it does not

Proved in this lesson

The drawingGroup() on the panel replay has panel-sized pixel extent, so its simple RGBA8 teaching estimate scales with panel pixel width × panel pixel height. The controlled route uses one position source for placement and crop.

Still not proved

The estimate does not include the ImageRenderer source image, the visible full-backdrop replay, exact GPU allocation, bandwidth, render time, blur cost, or dropped-frame count. Those remain separate measurements.

Evidence boundary: the browser SVG is a teaching copy of the route and the arithmetic. The iOS explorer executes a real ImageRenderer snapshot and a real drawingGroup() on the panel replay. It does not read the offscreen image back as a CPU pixel array, and it does not report GPU time. Do not use ultraThinMaterial or glassEffect as the glass path.
