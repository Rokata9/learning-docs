Chapter 6 · How SwiftUI draws the scene

Lesson 6.1 — View update, layout, and rendering

You can already build shapes, masks, and motion. This chapter now asks a different question: which part of SwiftUI decides what exists, which part decides where it goes, and which part turns it into pixels?

Practical problem: saying “SwiftUI redraws the screen” hides three separate jobs. If we do not separate them, later blur, capture, and backdrop explanations become impossible to reason about.
By the end

You will be able to follow one controlled card through view update, layout, and rendering; name the exact output of each phase; explain which later phase consumes that output; and identify which phase owns three common changes.

0 · PHASE CONTRACTS

Keep the complete frame pipeline visible

These are contracts, not timing formulas.

Terms before the pipeline: a phase is one stage of work. View update is the stage that evaluates a view’s body and decides which child views exist. A view is one item in that description, such as this card, title, or badge. A view tree records those views and their parent-child nesting. A frame is one complete displayed image at one moment.
Input state

Values before the phases

showBadge, contentInset, and cardColor describe the requested UI.

Next consumer: the phase that reads each value.

View update

What exists?

View body properties decide which views belong in the view tree.

Output: a view tree.

Next consumer: layout.

Layout

What size and where?

Layout measures views and places them in two-dimensional coordinates.

Output: measured sizes and placed positions.

Next consumer: rendering.

Rendering

What pixels?

Rendering turns the placed views and paint data into visible pixels.

Output: the rendered frame.

One-direction chain: state → view update → view tree → layout → sizes and positions → rendering → pixels. A later phase consumes the earlier phase’s output; it does not replace the earlier job.

Actual SwiftUI dependency boundary: which work reruns depends on where a state value is read. The iOS explorer puts badge existence in body, the inset inside Layout.placeSubviews, and the fill color inside a Canvas renderer. SwiftUI still constructs the Layout value from body when inset changes; the placement formula itself runs in layout. Reading the same color earlier while constructing the view tree would also cause view-update work.

8 · EXERCISES

Answer before opening the solution

Exercise 1 · What exactly leaves view update?

View update outputs a view tree: a description of which layout views exist and how they are nested. It does not output final pixel colors.

Exercise 2 · What exactly leaves layout?

Layout outputs measured sizes and placed positions for the existing views. Rendering consumes those results.

Exercise 3 · Badge removed

If showBadge becomes false in the controlled model, view update removes the badge view. Layout and rendering then have no badge view to process.

Exercise 4 · Does every color change skip view update?

No. It depends on where the state value is read. The controlled iOS scene reads the color inside a Canvas renderer, so that scene can invalidate drawing. If the color is read while constructing views or modifiers, view update may also rerun.
