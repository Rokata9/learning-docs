Resolution

Question: Lesson 8.4 split the rectangle at 80 pixels from the left. That 80 is a pixel count written into the function. It does not move when the rectangle gets wider. How does the shader learn this rectangle’s width and height?

Resolution in this lesson is the draw rectangle’s width and height, in pixels. Swift passes that pair as the extra argument resolution. The GPU reads the same pair on every call. splitX is half of that width, still a pixel count.

1 · THE NEW OBJECTS

Name resolution, the uniform slot, and splitX

Two different objects

fragCoord is this pixel’s position. Resolution is the whole rectangle’s width and height. A pixel at (40, 60) on a 400-wide rectangle has fragCoord = (40, 60) and resolution width 400. Those numbers are not interchangeable. You cannot compute “left half” from fragCoord alone.

Resolution

Resolution in this lesson is the pair (width, height) of the draw rectangle, in pixels. Swift reads the view size in points and multiplies by displayScale. Those values are pixels, not points. Lesson 2.5 already separated those units. At scale 1 they can match. On the iPhone 16 Pro, scale is usually 3, so they do not.

Uniform

A uniform in this lesson is the extra argument float2 resolution, after position, color, and scale. Swift passes a value into that argument. The GPU reads the same value for every pixel of this draw. The .metal file is not rewritten. Lesson 8.3 selected a different stitchable function to change color. This argument is only resolution. Other arguments are Lesson 8.9.

splitX

splitX is a name for half the current width, in pixels. splitX = resolution.x / 2.0. For width 240, splitX is 120. For width 400, splitX is 200. It is still a pixel count compared with fragCoord.x. It is not a 0..1 fraction.

Swift, once per draw of this rectangle: pixelWidth = pointWidth * displayScale pixelHeight = pointHeight * displayScale ShaderLibrary.halfOfResolution( .float(Float(displayScale)), .float2(Float(pixelWidth), Float(pixelHeight))) ← passes the pair into the compiled function ← does not compile a new .metal function
MSL, once per output pixel: fragCoord = position * scale splitX = resolution.x / 2.0 if (fragCoord.x < splitX) return orange else return navy ← every pixel sees the same resolution pair ← each pixel has its own position

Swift passes resolution once for this draw, on the CPU, before colorEffect fills the rectangle. Then the GPU calls halfOfResolution many times. Each call sees the same resolution pair and a different position. fragCoord is position × scale. resolution.y is the height in pixels. This split does not read it. The pair still needs two numbers because float2 is two numbers.

6 · iOS ROUTE
Pass resolution every draw

    

      
// shader/Resolution.metal
[[ stitchable ]] half4 halfOfResolution(
    float2 position, half4 color, float scale, float2 resolution) {
    float2 fragCoord = position * scale;
    float splitX = resolution.x / 2.0;
    if (fragCoord.x < splitX) {
        return half4(0.88, 0.48, 0.18, 1.0);
    }
    return half4(0.10, 0.25, 0.40, 1.0);
}

let pixelWidth = pointWidth * displayScale
let pixelHeight = pointHeight * displayScale
ShaderLibrary.halfOfResolution(
    .float(Float(displayScale)),
    .float2(Float(pixelWidth), Float(pixelHeight)))
// 8.4 leftover stays ShaderLibrary.splitAtEighty(.float(Float(displayScale)))

      

        
What each part changes

        
Xcode compiles halfOfResolution when it builds the app. Switching 240 pt and 360 pt does not compile a new function. Swift passes a new float2 into the same function.

        
.float2(pixelWidth, pixelHeight) runs on the CPU once per draw of this rectangle. The view’s width and height are points. Multiply by displayScale before the call. The shader compares pixel fragCoord with half of that pixel width.

        
240 pt is a teaching width so the 8.4 leftover of 80 pixels still sits inside the narrow card. It is not glass geometry. On the iPhone 16 Pro, 240 pt is usually 720 pixels, and the 8.5 split still sits at half of those pixels.

9 · EXERCISES
Answer before opening each hidden solution

    
What is resolution in this lesson?
The draw rectangle’s width and height, in pixels. Swift passes that pair with .float2(pixelWidth, pixelHeight) after multiplying the point size by displayScale.

    
Diagnostic: can the function compute “left half” from fragCoord alone?
No. fragCoord is this pixel’s position. Half of the rectangle needs the rectangle’s width. That width is resolution.x, not fragCoord.x.

    
You switch 240 pt to 360 pt. Does Xcode compile a new stitchable function?
No. halfOfResolution stays. Swift passes a new resolution pair into that argument. At scale 3 the pixel widths are 720 and 1080, so splitX is 360 and 540. Lesson 8.3 selected a different function because the return color changed.

    
A pixel has x=150 on a 400-wide rectangle. What does 8.4 store? What does 8.5 store?
8.4 compares 150 < 80, which is false, so navy. 8.5 compares 150 < 200, which is true, so orange. That pair is the proof that the baked 80 does not follow size.

11 · EVIDENCE BOUNDARY
What this lesson establishes

    

      
Established
The shader does not receive the rectangle’s width and height as part of fragCoord. Swift passes that pair as the argument resolution, in pixels. splitX = resolution.x / 2.0 is half the current width in pixels. Changing the view width passes a new pair without compiling a new function. The 8.4 leftover of 80 pixels does not follow size.

      
Not claimed
This page’s fill is not a GPU compile. Dividing position by resolution to get a 0..1 pair is Lesson 8.6. Color, time, and other arguments are Lesson 8.9. A missing argument is not measured here. half versus float is Lesson 8.7. Chapter 7 frost is unchanged.
