Chapter 1 · Lesson 3 of 8

Create LiquidGlassLab and prove the iOS baseline

This lesson creates the separate Xcode project. It proves that your build tools, your iPhone 16 Pro connection, and SwiftUI all work before we add any glass effect.

No Liquid Glass is implemented in this lesson. That is deliberate. A known-good baseline lets us separate future graphics mistakes from project, dependency, or device-connection mistakes.

Small lesson goal

At the end, the iPhone 16 Pro shows three lines of text:

  • Liquid Glass Lab
  • Chapter 1 · iOS baseline
  • No glass effect is implemented yet.

Main engineering idea: first prove the simplest complete path from source code to visible pixels.

New math: none.

1 · What the baseline proves

One visible result can prove several separate systems

A successful editor preview is useful, but it is not the same evidence as a successful run on the physical phone.

Build proof

Xcode can turn the project source into an installable debug app bundle. The bundle suffix is .app.

Evidence: the build completes without an error.

Connection proof

Xcode Run, or devicectl, can communicate with the iPhone 16 Pro. That channel is the tool that installs and launches a debug build from the Mac.

Evidence: Xcode lists the iPhone 16 Pro and installs the app.

Rendering proof

iOS starts LabApp. SwiftUI creates the text views. iOS draws them on the phone screen.

Evidence: the exact three lines appear on the iPhone 16 Pro.

Baseline means a simple result that is already known to work. We will compare later results against it. The baseline is not a graphics effect.

3 · Code-driven teaching preview and coding challenge

Three version numbers have three different jobs

Edit the code or click the controls on the right. Both paths update one shared state.

SDK_VERSION

The iOS software development kit, abbreviated SDK, that the compiler lets your source code reference. This is a teaching name for the SDK that ships with your Xcode.

Question answered: “Which iOS API names may this source code compile against?”

IPHONEOS_DEPLOYMENT_TARGET

The oldest iOS version on which the package is allowed to install.

Question answered: “Is this device new enough to run the app at all?”

TESTED_IOS

The iOS version this course has actually been run against. iOS does not have a third install-or-compile build key for this job. This number is a course declaration, not an Xcode setting that changes system behavior.

Question answered: “Which iOS version is the tested floor for this course?”

7 · Run on the iPhone 16 Pro
Verify the physical-device path

        
This section performs Run B, the course-baseline run. Run A, the untouched-template proof, must already be complete. Use USB first if you have not already enabled network pairing because USB removes one network variable from the first device check. Simulator is extra evidence. It is not the Lesson 1.3 proof.

      


      

        

          
Enable Developer Mode
On the iPhone 16 Pro, open Settings → Privacy & Security and enable Developer Mode. Restart when iOS asks. Developer Mode permits Xcode to install a development build after you trust this Mac.

          
Connect and trust this Mac
Unlock the iPhone 16 Pro. Connect the USB cable. Tap Trust on the phone if iOS shows the trust dialog. Trust is the pairing check that prevents an unknown computer from silently installing apps.

          
Select the iPhone 16 Pro in Xcode
Use the destination control near the Run button. The chosen target must be the physical iPhone 16 Pro, not a Simulator.

          
Press Run for the course baseline
Xcode builds the debug configuration containing the supplied Swift files, installs the .app bundle, and asks iOS to launch LabApp.

          
Compare the exact screen
Confirm all three lines. A blank screen, a template greeting, or a crash is not the checkpoint result. The chapter picker may appear above the three lines. The three lines are the baseline.

          
Save evidence
Take one iPhone screenshot and save it under your preferred learner-work location. Record the device iOS version shown by Xcode or Settings → General → About.

        


        

          
Expected result
The app launches without a crash. The phone shows the baseline title, chapter label, and explicit statement that no glass effect exists yet.

          
iPhone 16 Pro does not appear in the destination list
Unlock the phone. Reconnect the cable. Open Window → Devices and Simulators and wait until the device is ready. Enable Developer Mode if iOS still blocks development installs.

          
The device appears as untrusted
Unlock the iPhone 16 Pro and tap Trust. If the dialog never appears, unplug, replug, and unlock again. On the Mac, confirm the device in Devices and Simulators.

          
I prefer a network connection
First complete one USB run when possible. For Wi-Fi, place the Mac and iPhone on the same network. In Devices and Simulators, select the iPhone 16 Pro and enable Connect via network. Select the same device in the Run destination and run the same scheme.
Network pairing changes only the computer-to-device transport. The Xcode build, .app installation, LabApp launch, and SwiftUI rendering stages remain the same.

          
The iOS SDK platform is missing
Open Xcode → Settings → Platforms. Install the iOS platform for this Xcode. Then build again.

          
Xcode is too old for this project
Update to Xcode 16 or newer. Do not solve this by pasting unrelated build settings from old tutorials. Keep the template-generated tool versions together. Deployment target stays 17.0.

          
LabTheme is unresolved
Confirm ui/theme/Theme.swift, Color.swift, and Type.swift sit under the synchronized LiquidGlassLab/ group. This mismatch occurs when a file is outside that folder.

          
The bundle identifier does not match my project
Replace com.example.liquidglasslab in the Xcode target with the identifier you selected. Keep that identifier consistent in every place that names the bundle.

        

      

      
macOS boundary: Xcode runs on macOS. Build and device install for this lab happen on this Mac. A Windows or Linux machine cannot compile the iOS app. Simulator is extra evidence, not the Lesson 1.3 proof. The physical iPhone 16 Pro is the source of truth.

    


    

      

        
8 · Exercises
Answer before opening the hidden answers

        
These questions diagnose whether the three version numbers and the evidence levels are still being merged into one idea.

      


      

        

          Exercise 1 · SDK roles
          
Which value controls the oldest device that may install the app?

          
          
Show answer
IPHONEOS_DEPLOYMENT_TARGET. With deployment 17.0, an iOS 16 device is rejected and an iOS 17 device is allowed.

        


        

          Exercise 2 · Diagnostic misconception
          
Does compiling against the iOS 18 SDK make an iOS 18-only function exist on an iOS 17 phone?

          
          
Show answer
No. The compile SDK controls which API names the compiler accepts. The runtime device still contains only the APIs delivered by its iOS version. Code that calls a newer-only API needs an #available check or a compatible alternative.

        


        

          Exercise 3 · Evidence
          
A debug build succeeds, but the iPhone 16 Pro screen has never been checked. What has been proven, and what remains unproven?

          
          
Show answer
Proven: the project model resolved, the source compiled, and a debug bundle was produced. Unproven: device pairing, installation, LabApp launch, SwiftUI execution on the phone, and the final visible result.

        


        

          Exercise 4 · Trace
          
Write the source-to-screen path in order.

          
          
Show answer
One acceptable path is: Swift source → Xcode build → debug .app → Xcode Run / devicectl install → iOS launches LabApp → WindowGroup presents LabHost → Chapter01Screen declares the visible user interface → SwiftUI text views are drawn on the iPhone 16 Pro.
