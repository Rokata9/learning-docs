# AGENTS.md — Liquid Glass Learning Documents

The rulebook for the interactive learning documents. Keep this file short. Merge new rules into existing ones. Delete superseded rules. A rulebook too long to remember is worse than a short one.

## Scope and files

- Course home: `liquid-glass-course.html`. Chapter hub: `lesson-[chapter-name].html`. Sub-lesson: `lesson-[chapter-number]-[lesson-number]-[lesson-name].html`.
- Every lesson is one standalone HTML file that works from `file://`: inline CSS, JavaScript, SVG. No external libraries or CDNs.
- iOS source lives in the sibling repo `/Users/rosen/Code/LiquidGlassLab-iOS`. Never create `ios/` or `android/` here. When a revision changes iOS code, state the exact Swift target path; when it changes none, say so. A lesson whose excerpt shows Metal or Swift ships those files, wired into the chapter screen and built, in the same session; without the lab or Xcode, tell the learner before generating instead of shipping an uncompiled excerpt.
- No ZIP archives unless the learner asks. Edit the two repos in place.
- Desktop only: verify at `1920×1080` or larger. Light theme only for lessons.
- Do not store lesson completion counts, checkpoints, generated frontiers, or completion/generation status in project files or course pages. Report the learner-confirmed count only in chat when generating a new lesson. The iOS demo selects the latest chapter on a cold launch and brings its chapter chip into view.

## Language — the top rule set

1. Plain English for a non-native speaker. Short sentences. One idea per sentence. No idioms. A stepper caption is a short list: one sentence per line, about 14 words at most, and at most about 10 lines; a step that needs more is two steps, or its numbers move to the table. A line that announces items (“two things:”, “Compare with …:”, “Repeat Steps 6–8:”) carries those items as nested sub-points under it, never as lines at its own level. A reason gets its own line, as a question and its answer (“Why a board? Near one pixel, the glass is almost flat.”). Never fold a reason and a comparison with an earlier step into one sentence (“We use a board because …, as the rim was … in Section 1, Step 9” failed); point at a picture on the same screen instead. A colour name used as an object name ("the light-green curve") must mean one object in the whole lesson. Never chain several quantities in one sentence (“one small step further in adds the step and takes away what the push loses, so …” failed): show the change as a picture with colored numbers instead.
2. Define every term at first use, in the same sentence. Notation is a term too: before numbers in brackets such as (−3, 1) or a part letter such as z appear, a drawn example says what each position means (x part, height part). Add a small `ⓘ` tooltip for anything that may need a refresher: an older formula, an older lesson's object, a chosen constant. Tooltips carry reminders only; the page must be fully understandable without opening them. A word that could describe a graph or the picture (linear, straight, smooth) must say which one it describes. Each section re-anchors the objects it draws in a legend beside its first picture (colour swatch + one line); never rely on a definition from another section. Do not describe how the page computes a value (search, bisection) unless the learner needs it. A lesson may assume only earlier lessons in curriculum order and any prerequisite the learner explicitly names in the current conversation; an idea from a later lesson counts as new, even if a side lesson sits next to it. Before writing, grep the prerequisite lesson files for every term, formula, constant and code construct the lesson uses; explain each one that is not there, in this lesson, where it first appears, with the numbers (a tuning constant, a font measure, a time constant: say what it is and where it comes from; for a tuning constant also say whether it is a property of the material or a chosen dial (a chosen number in a formula, such as the walk of 1 that becomes the height part 1, is called “chosen” where it is used, with what another choice would give), and show what other values would do). Put a “Before you start” panel near the top: what is used from the course, with lesson numbers, and what is new here, each with a one-line meaning and a link to where it is explained. A code excerpt gets a line-by-line table (line · what it does · taught in) that marks every construct the prerequisite lessons do not teach as new and explains it in that row. Banned words: `arctan`, “lattice”, “level-set”, “X is not an input”. “Amount” means the Lesson 7.10 slider until a later lesson redefines it.
3. One object, one name. Never rename a thing mid-lesson. An arrow named after a direction (“x walk”) says, where it is defined, whether it lies along that direction; the x walk on a tilted board is not along x (x is always level). Keep the names of a quantity's parts the same from the section that introduces them to the end (x part, y part, height part, shadow, length); code names (rawNormal.x, .z, x², z²) appear only in the code sections (code excerpt, coding challenge, Metal exercise), translated where they first appear (.x = x part, .z = height part), and every formula outside them uses the part names (√(x part² + y part² + height part²), never √(x² + y² + height²)), and a length computed again later uses the same steps as when it was introduced (shadow first, then length). A traced-value card applies a recipe that an earlier section built; it does not redraw the helper objects of that derivation (the walks) unless its own lines use them: card 4 drew and computed two walks that no later line used, and the learner asked why they were there. Show the result's meaning with objects already on screen instead (rawNormal's square corners with the two glass curves, in the front and side views). Name a chosen number by what it is, “height part = 1 (chosen, always 1)”, never by its history (“the turned walk of 1”). A view of an object is not a new object: write “rawNormal, seen from the front: (0.45, 1)”, never a coined “front arrow” or “side arrow”. No metaphor names such as seat, stick, landing, net, or depth: call the object by its plain name — pixel, arrow, output position, the box's height. A direction word (along, across) names the line or circle it follows, defined and drawn in the same state. Never change the case of text that can hold a name or symbol (no `text-transform: uppercase`: it turned ρ into Ρ, read as P, and e into E). Table headings use the picture's names (W.x, not point.x), typeset formulas as math, and say in words what each symbol is (e: the distance from C to P). Never add a second word for a quantity that already has a name: “depth” and “deeper” for Section 2's inside confused the learner; use inside, “further inside” and “nearer the outline”. A reference line such as the top edge is defined once with a picture (and its coordinate) before any step measures from it, and a picture that turns a vertical line on its side shows that turn. When a name needs a mental translation before the picture makes sense, use the visible role instead: “upside-down copy” rather than “copy 1”, “original-order copy” rather than “upright”, “the line y = 0.50” rather than “pixel row” or “glass-picture row” (never “row”, “column” or “cut along the row”: the learner found “row” unclear across several lessons), and “top of the glass” rather than “top edge”. Do not use band/width for a region whose meaningful measurement is its height. A side view of the glass is a “slice along the line y = …” (or x = …); the first slice in a lesson is introduced with a 3D picture: the line on the screen, the glass cut straight down along it with the front half removed, and the cut face, beside the flat slice. Every slice prints values on its axis (x 0.65, y 0.381: outline). A slice whose line does not pass through C carries a small from-above map with its line, C and the flat-top circle, and says which parts it cuts (the line x = 0.72 cuts only the rim; its middle is y = 0.50, not C).
4. Never point back vaguely. Forbidden patterns: "between the two", "the former", "that value", "those moves", "other points", "the same amounts", "near one pixel" (name the pixel: W, and the patch: from above A to above B), and it / its / this / they when the noun is not in the same sentence. Repeat the object's name instead. Points used in a claim get names in the picture (P₂, P₃) and their numbers in the table, so “the same” is shown as two equal results.
5. Every purpose statement is followed by its reason in the same or the next sentence. "We multiply by falloff **because** …" Nothing is taken for granted. A drawn helper (legs, construction lines) is a purpose too: the caption says which number it gives and which formula needs that number, and the picture draws it whole, its start point included. A helper that leaves the surface it measures says why, in its label and caption (a level leg above a tilted ramp: “level, in the air above the board; the walk itself lies on the board”). A helper drawn at only some objects (circles at two of nine pixels) says why those; otherwise draw it at the step's own object. When a lesson picks a specific tool where an obvious simpler one exists (smoothstep over a straight line), state why the simple one fails and show the comparison picture: an in-place toggle on content that reveals the difference, with a magnifier when the difference is small. Say with a number how big the difference is and on which content it shows.

## Visuals first

6. A picture carries the explanation; prose captions the picture. Every picture shows where each of its points comes from (an output pixel joined to its read point; the line from C through it), prefers the real scene to scale with many lines over a symmetric schematic, and stands beside at most two sentences; never print a derived number without saying which direction or object it belongs to. If a paragraph describes something a picture could show, draw the picture. Prefer interactive pictures (toggle, drag, slider, stepper) over paragraphs. Show examples instead of listing them: if the text names real content (text rows, icons), a picture shows it. When an effect moves or reshapes content, let the learner pick a piece of it (a word, a cell): tint it in the source, give every output pixel that reads it the same tint, and keep the tint while the control moves. Draw the effect large enough to see at a glance. When an explanation depends on where pixels read, draw it with arrows from output pixels to their read points, stacked the way the read really moves: with C above the read moves up (wallpaper on top, output below, arrows up); under the straight top of the glass it moves down (output on top, original picture below, arrows down). Add marks for what the arrows show (×2 for a source pixel read twice, ✕ for one never read). Its caption is at most four short sentences; tables of numbers stay visible under the picture, never in a collapsed box (the learner reads the calculations beside the picture). When the read points and their pixels are far apart, draw one window of the screen split by a black line (the wallpaper on C's side, the output beyond, one shared scale) so lines from C and the arrows run straight across it; do not split it into pictures plus magnifiers whose frames look like objects. Start from the effect the learner can see: the first picture zooms on it and marks it with a labelled bracket, and a caption names an effect (mirrored, folded) only when that picture shows it at a glance. When the real scene is busy or moving, study the effect first on a still test case built to make it readable (stripes numbered by their distance from the edge, each with an arrow that turns around when the stripe is shown upside down), then return to the real scene. A chain of pictures that produces the output (page → glass picture → output) is drawn as pictures side by side joined by arrows, each with its name as its title. When the lesson relies on an imagined 3D shape (a surface height), give a turnable 3D view (drag to turn, wheel to zoom, preset views), cut along the line the lesson follows, beside the flat side view of that cut at the same scale; arrows go from the surface point above a pixel to its read point, so the direction of every push is drawn. Before the lesson reasons in 3D, it introduces the view in its own steps: the flat view from above first, then a tilt that adds height (one point given as three numbers). Every 3D picture carries a small corner box: its coordinates and the x, y and height arrows as drawn. No eye-position guidance anywhere: no eye icons, phone or monitor metaphors, “stand at …”, “your eye”, or “looking down 30°” (the learner found it unhelpful, 2026-10-30). The tilt step says that x, y and height are fixed directions (x toward the right edge, y toward the bottom edge, height up) and that turning the view changes only their drawing; a point above a pixel keeps the pixel's x and y. Before the first single-view argument, one step shows one walk with its three numbers and the same walk from above, from the front and from the side, each small picture saying which two numbers it shows and which one it does not show. Name views plainly (view from above, front view, side view) by the two directions each shows, never “look along y”. A part along the third direction is “not shown in this view”; when a drawn object still shows a line in that view, say which of its parts the line is (in the front view the y walk (0, 1, −0.60) is a line straight down: its −0.60); never write “you cannot see any y part” beside a visible y-walk line. A walk or arrow is never presented as a second coordinate system: it is the change of the same x, y and height from its start to its end. A 3D step that repeats a 2D argument shows that 2D picture beside it, drawn as in the earlier section. After the lesson has introduced 3D, pictures of the surface are turnable 3D views in UV (learner request 2026-10-30: “only 3D from now on, that's the real deal”): zoom on the traced point, draw a small floor patch with its UV range, the two lines through the point, the glass surface along them as 3D curves, posts for heights and arrows from H with a stated arrow ruler; draw no whole-glass mesh at that zoom (it buries the posts) and say in a label where C lies. Flat side views stay only where a section teaches the side view itself. Before placing an effect label (upside down, mirrored), look at the pixels under it: if the effect can look like something else on real content (upside-down letter bottoms look like letter tops, so a folded word looks merely stretched), color the source by position (letters by their distance from the edge) so the output shows the reversal, and say in one sentence why it is easy to miss. When the lesson says the real recording shows an effect, show the clearest real frame beside this page's sharp render of the same moment, mark on the frame the features that prove the effect (a b closed at both ends), say why the frame cannot show more (resolution, blur, only part of the letters folded), and state any mismatch between this page and the frame with its size. A draggable pixel gets the full chain for that pixel, every line in order (its sd, inside, h, push, outward from the four neighbor sd values, read point, and the color found there), so the learner can follow any position, not only the teaching one. Show that chain in a draggable window that opens when the learner clicks a point of the output (closes with ✕, Escape, or a click elsewhere), not as a permanent panel that pushes the pictures off the screen. Arrows that overlap and cross do not explain themselves: first give each element its own row (one row per pixel: the pixel, its arrow, where it lands), with the change from the row above as colored chips (+1 moved · − push lost · = read point moved), and only then show them together. Show a consequence on an object whose mirror image looks different (a color ramp, a triangle that becomes an hourglass, an L that becomes a [), never on symmetric stripes. When the real content's folded part looks like itself (a b's bottom strip, so the folded b reads as a stretched b), say so, and draw beside it a letter whose fold is unmistakable and the same letter only stretched. No gray text blocks of reasoning or calculation: a readout holds numbers in a table with colored columns that match the picture; reasoning goes in short captions beside the picture that shows it, and an optional derivation goes into a window with its own picture.
7. Label every drawn element inside the picture: rings, arrows, points, regions. If a label does not fit, put a numbered tag on the object and name the tag in the adjacent text on the same screen. Every chart says in one sentence beside it what one bar or mark stands for. The reader must never guess which drawn object a number or sentence refers to. When a slider or drag can produce shapes the lesson has not named (turned-around words, loops), a picture next to the control names each shape and draws where it comes from. A legend lists only what the current state draws (this step, this part); every letter in the state's table is drawn and labelled in its picture. Match parts of two pictures by marking the same piece names inside both pictures (colored bars with letters), not with ribbons or connectors drawn between them; the step's first sentence says what the step adds to the steps before it.
8. Text must match the picture exactly. If the text says "three arrows", count the arrows in the picture before shipping. Plot only real values: draw a jump as two separate pieces, never as a vertical connector, and put no mark on a connector. Every point or object named in the text or a readout is drawn and labelled in the picture, and every distance, width or difference names its two points (from L to R) right where it is printed, and both points are drawn in the same picture (zoom out until both fit; a magnifier shows the small part). A caption that describes a motion names its direction, and every “first … then” order is checked in that direction. Read points are drawn on the wallpaper picture, never on an output picture that differs from it; a magnifier shows the same picture as its source. When a pixel's color is explained by where it reads, draw the whole chain: the pixel in the output, its spot and push arrow (with the push length printed) on the wallpaper, its read points, and one arrow per channel from each read point back to the pixel; pixels that share a line are shown one at a time with a chooser, never stacked. Print the push next to the small spacing it is compared with (0.10 versus 0.01).
9. A sequence that builds up gets a stepper: one new object or operation per step, and the picture must visibly change at every step. A caption-only change is a failed step. The picture must also render at full readable size at `1920×1080` (SVG labels ≥ 14 px on screen); a layout that squeezes a wide diagram into a narrow column fails. Use the fewest steps the causal chain needs, and let every control, calculation and picture read one shared state.
10. Every plotted point is clickable: a tooltip shows its name, role, and coordinates in their named coordinate space. Clicking a point must not move or select anything else; a click that also redraws (picks a letter) reopens its popup on the redrawn element. Support Enter/Space, close button, outside click, Escape. Keep the popup inside the viewport. Every point stays inside its picture: a zoom that follows points fits all of them, lowering its factor and printing the factor it uses. When real points are too close to activate, add an enlarged inset of the same picture and print its horizontal and vertical zoom factors; never move points to fake positions just to make them clickable. A selected point’s coordinates and full calculation stay visible beside the picture, not only in a transient tooltip. When the learner selects a point in the original picture, the arrows still run from its output pixels to it, in rule 6's read direction. Every point the learner can place or select (a traced pixel W, the points of a projection picture) is also draggable, in every picture that shows it (an enlarged inset included), and goes exactly where the pointer puts it (never snapped to a line; any rounding stays under one screen pixel): the matching points, arrows, coordinates and calculation follow the pointer live, and a press without a move stays a click. Offer a view of points evenly spaced along the whole shape with all their projections, spaced so no two dots overlap; show crowded ones in the enlarged inset, never hidden or moved. Images and the points drawn on them share one scale and origin.
11. Construction strokes need a dark halo plus a hue that is not in the picture: on the orange/navy checker cyan, lime, pink, violet, white; on a picture that itself shows red, yellow, cyan or blue (color fringes), violet, orange, pink, lime. Solid strokes, not dashes. Canvas labels take dark or light ink from the pixels under them; a label that crosses light and dark pixels sits on a light plate.

## Formulas — always fully expanded

12. Every displayed calculation shows, in order: the named formula → the substitution with every input visible → every intermediate value → the result → what consumes the result. Never print only a result. Each “=” does exactly one operation, and every line is rounded the same way (3 decimals by default; squares that feed a √ are exact), so a calculator reproduces every line — everywhere a number appears: text, generated readouts, tooltips, canvas labels, table cells. The reader never does arithmetic in their head outside the exercises. Every number says what it measures and on which scale (a channel from 0 to 1, UV, pixels of a stated size), most of all when two different quantities print the same number: innerHalf.y = 0.20 − 0.10 = 0.10 was read as the corner radius 0.10, so name both beside the number and say the match holds only at this value. A count lists what was counted and by which rule (a table of the items, or numbered marks in the picture); a ratio says in words what it divides by what. Round only where rounding cannot change a comparison or a count (use more decimals for points closer than 0.001). In a walkthrough of many items (one row per pixel), every item shows its own full calculation right beside it, so the reader never has to remember a number from an earlier step. A comparison between two items is written in words with its subtraction (“push 6.357 shorter, pixel only 1 deeper: read point 6.357 − 1 = 5.357 pt nearer the outline”), never as signed chips such as “−5.357 back” or “+1 − 6.357 =”. When a ratio converts between two scales, draw both totals divided into the same number of equal parts, name the numerator’s total and the denominator’s part count, and trace one +1 input through the rule; never introduce the bare ratio. Use the original integers for a reciprocal (28 ÷ 24, not 1 ÷ a rounded 0.857143). Generated arithmetic must be calculator-exact from the displayed inputs at every slider position, not only at the teaching value.
13. Attach a `ⓘ` provenance icon to any value that comes from elsewhere: an earlier lesson, a slider, a fixed constant, a previous step. One line inside: origin, representation, consumer.
14. When an older formula is reused (smoothstep, length, source-over), refresh its mechanics right where it is used: inline if short, in a `ⓘ` tooltip if long. State what goes in and what comes out. A pointer such as “card 8” or “Section 3” is not a refresher: the formula and the source of each of its numbers appear on the same screen. Inside a chain, a line that adds, subtracts or divides by a constant says why (sd − (−0.10): how far sd is past −0.10, where the smoothstep band starts).
15. A claim of change, sameness or shape ("grows", "the same everywhere", "stays straight", "bends", "smooth") is immediately followed by the numbers or the picture that prove it. Show a rate ("slope", "how fast") as the drawn difference between neighbouring samples at a stated step, never as a bare rate such as −5, and show what the rate changes in the picture. Numbers that prove a shape are drawn too (the gap on the picture); an effect word (break, corner, copies) is defined by pointing at it in a picture. A claim that a color change is strong or weak draws channel bars for every color involved and prints every channel's change, not a chosen few. A color-coded display map (slope colors, normal colors) gets a reading figure in the lesson that introduces it: the map with numbered points around the whole shape, the colors stored along one line with every channel drawn as a curve on the same x scale under a slice of the surface, a table from the value to each channel, and one sentence on where the color is plain and where it changes, compared with the previous lesson's map. A distortion is explained by following several labelled points of the shape (its ends, middle, top, bottom) through the whole formula, step by step; each shape word (bends, longer, thinner) is derived from those points' numbers and drawn as a bar between two named points, before and after. A same-factor argument reads “k times as far → k times as wide”, with k computed on both quantities and each quantity drawn as a bracket between its ends; it says when it holds (any triangle, if both ends get the same k) and computes each end's own k when they can differ. When a value has no short formula, give its equation, read it off a drawn chart, and check it in a table. A value the lesson finds (a fold line, also for other dial values) is found in the main flow with reasoning the learner already has: a crossing on a drawn chart whose curve is built from steps they followed, checked just before and just after the crossing. A formula cited from an optional window, or a table of results, is not an explanation. An optional derivation window follows the same rules: every fact it uses is either from the prerequisite lessons or stated with an everyday picture and checked with numbers (a circle's edge at a right angle to its radius: measure the climb over a tiny step), and it never solves for an unknown with algebra the prerequisite lessons do not teach. When an exact closed form can be derived using only math already taught, present its derivation and use it before any numerical search. A numerical search is a fallback when no suitable exact form exists, or a check after an exact result; it finds the value by trying and narrowing one decimal at a time, with zooming rulers and the full numbers of each try. Never let a numerical check replace an exact formula merely because the formula needs a carefully drawn derivation. A stretch factor says what it measures (a length along a stated direction, or an area); an area factor made of two length factors is drawn on one small square of the shape, before and after each factor (1 × 1 → k₁ × 1 → k₁ × k₂), with the shape drawn straight at one scale around it. When the learner asks why something holds, give the proof first, in one or two sentences, then one picture that shows exactly that proof (for “no missing pixels”: every output pixel's read point as a dot on the wallpaper, and a clicked pixel's read point in the middle of its neighbours'), plus a toggle to the way that fails (pushing pixels forward leaves holes). Showing data is not a proof: no walkthroughs, mini-charts or text blocks that do not carry the argument. A claim that a slanted stroke bends is proved by comparing at least two consecutive moves: draw each move’s horizontal and vertical parts and compute right ÷ down (or right ÷ up). A bare “horizontal change per row” or “uneven vertical spacing” is not the explanation.

## Lesson shape

16. One main graphics idea and at most one main mathematical idea per lesson.
17. Short lessons: one concept, then stop. That is why the course has 216 lessons. The idea must be complete after the first two sections. Do not prove side facts (why a curve has no corner, where a peak sits, an exact region shape): a side fact gets one sentence, one picture, or a pointer (a pointer to a later lesson says that this lesson does not need it). Q&A answers stay short and never grow into proof rounds. No warm-up sections: one preview sentence in the hero, then the point. Each later section must add a new object, a new operation, or a new consumer — never restate earlier content. A requested rewrite redesigns the lesson from this rulebook: do not keep the old section skeleton, the old steppers, or proofs already taught in an earlier lesson (point to that lesson in one sentence). Only the rendering engine and the verified numbers may carry over. When a result has an obvious next question (is the fold symmetric? why is one copy squeezed and the other stretched?), answer it in its own step with numbers and a picture. A learner's “why does this shape look like that” question is answered in the lesson with a new picture, not with a chat table: a bend is shown as stairs along the stroke (per row of the picture, how far down and how far sideways it goes, before and after), with a toggle to the case that does not bend. Define every comparison case with a picture before using it, and open it with the question it answers (“does every rim fold?”) (a “straight ramp” is first drawn next to the quarter circle, with h = pixel shown in a table). Keep pictures readable: few, widely spaced lines, each labelled; never a dense web of curves. An explanation made along one special line (under a straight edge) says whether it holds elsewhere (around a rounded corner) and shows in its own step what changes there. New-learning gate: every full lesson adds a genuinely new mechanism, API behavior, math operation, measurement method or implementation step; a recap is brief and serves that step; material that is mostly consolidation becomes a short checkpoint or merges into the next lesson.
18. Required scaffold, in order: visual hero → the idea in pictures → one fully traced value (pick the teaching pixel so the lesson's new line changes its stored value; put it on an axis through C when possible, so only one coordinate moves) → interactive lab → short code excerpt → coding challenge → 2–4 exercises with hidden answers (each exercise opens with its picture, every named point drawn and labelled, says in words which code line changed and what that line does, which idea of the lesson it checks and why, and what the learner does to answer (which facts to read off the picture, which line combines them), and asks one question, the same as its title, with 2–4 clickable choices; each hidden answer draws the reason) → Metal exercise (the learner writes at least one meaningful Metal function — more than a few lines, joining this lesson with earlier ones — in a lab file whose stubs compile; the calling code is prepared: a stitchable caller in that file, an answer-key shader with `static` helpers, and a check view on the chapter screen that draws yours over the key with `.blendMode(.difference)` and `markDifference` paints red where they differ; the page shows the goal picture, the signatures with doc comments, test pixels with target values, the prepared code, and a hidden answer with every number) → copyable Markdown record. State when the browser model differs from iOS. Separate what we see from what the framework does internally; label estimates as estimates.
19. Keep each walkthrough state self-contained: repeat the current values beside the formula that consumes them, so the reader never scrolls back to decode a substitution. A stepper's numbers table sits directly under its pictures, above the legend; beside a side panel taller than the pictures, so pictures and numbers stay on one screen. When a derivation puts one formula into another, show the inserted formula on the same screen, color the inserted part like its source (for sums of squares: one bar per squared number, the sum drawn as the same colored bars end to end, so √(x part² + y part² + height part²) is one bar of three pieces; never write “the first root is not needed” without that picture); for a change of range (× 0.5 + 0.5 from −1…1 to 0…1): number lines on one shared scale, one line per operation, the target range shaded as a zone, dashed lines for where the two ends go, real values marked on every line, and the reason said first (a color channel cannot hold a value below 0); never two lines at different scales, where the learner could not tell what the −1…1 line and the 0…1 line under it were for). A table of values that come from a chain (the color guide's N per point) gives every row an ⓘ with that row's complete chain, the input chains included (the four heights), at enough decimals that the chain rounds to the table's value; its last line says the table rounds (5 decimals for the color guide: with 3, the diagonal points came out 0.711 instead of 0.709), do one move per line named in words, and check every line in a numbers column. When a table's rows belong to different pictures or parts of a picture, heading rows group them by picture (on the wallpaper / in the output / compare). Never use a value that a later section computes (no “from Section 2” inside Section 1): the idea sections use round, given numbers on the test case, never 0 or 1 and never equal to another number on the same screen; when an inherited teaching value is 1 or −1 (slopeX at W), every line names what its number is (x walk height part = slopeX × 1 = (−1) × 1 = −1; N.x = rawNormal.x ÷ normalLength) and the section says so once; once a section is in 3D, every arrow is written with three parts ((1, 0, −1), never (1, −1)) (a slope of −1 next to a walk of 1 read as “always 1”; start from a 3-4-5 ramp and show 1 later as one case), and the long chain from the inputs (springs → … → color) lives only in the traced-value section, as cards in reading order, each with its own small picture. Every printed position names its coordinate system, origin and axes (pt from the test picture's top-left corner, y down); a bare “x = 257 pt” is a failure. Every picture names its system in a label inside it (UV, a side view in UV, polar, a made-up test grid, 3D test units; in a 3D picture the first line of the corner box). A lesson with more than one system lists them in a panel near the top: label · where used · origin · axes · unit, plus how arrow parts are counted (from the arrow's start, in its picture's unit), that picture pixels are only a scale, and whether polar coordinates are used. The caption of the step that switches system says so; one picture never mixes two systems unless it prints the conversion.

## Verification — non-negotiable, in this order
