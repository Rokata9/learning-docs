The earlier curriculum title called the result of Lesson 1.1 an “Android library module.” That was one step too early. 02 · DEFINITIONS

The ten terms used in this lesson

These definitions are also added to the course glossary.

Gradle

The build-automation tool used by this project. Gradle reads configuration files, creates a build model—an in-memory description of projects and tasks—and runs requested tasks. A task is one named unit of build work.

Root project

The top-level Gradle project for the repository. In this source tree its name is Photos.

Subproject

One registered build unit inside the root build. Gradle documentation also uses this term for what Android Studio commonly calls a module.

Settings script

The root settings.gradle.kts file. Gradle reads it to discover which projects belong to the build.

Project path

Gradle’s identifier for a project inside one build. :tiled-engine is a Gradle project path, not a filesystem path.

Project directory

The physical directory assigned to a Gradle project. The default directory for :tiled-engine is <Photos root>/tiled-engine.

Registration

The act of adding a project path to the Gradle build model through the settings script. Creating a directory alone does not register it.

Kotlin DSL

Gradle configuration written with Kotlin script syntax. The suffix .gradle.kts identifies a Gradle Kotlin DSL script.

Gradle plugin

Software applied to a project to add and configure capabilities and tasks. The Android library plugin is deliberately applied in Lesson 1.2.

Build script

A project-level file such as build.gradle.kts that applies plugins and configures that project. Lesson 1.1 does not create this file.

Keep three facts separate: a directory can exist, a Gradle subproject can be registered, and an Android plugin can be applied. Lesson 1.1 makes the first two facts true. The third remains false.

  • The command exits successfully.
  • The output identifies Root project 'Photos'.
  • The project hierarchy contains Project ':tiled-engine'.

What this proves

Gradle read the settings script, found the directory required by the registered path, and created a subproject entry named :tiled-engine.

What this does not prove

It does not prove that the project is an Android library, that it has Android tasks, that the app compiles, or that any native library exists.

08 · EXERCISES

Answer without opening the hidden answers

Send your answers in chat when you complete the lesson.

Exercise 1 — A tiled-engine/ directory exists, but there is no matching include(...) call. What does Gradle know?

Answer: Gradle does not know that the directory is a normal subproject in this build. The operating system can see a directory. Gradle registration is a separate fact established by the settings script.

Exercise 2 — The settings script registers :tiled-engine, but the directory is named tiled_engine. Why does the default mapping fail?

Answer: The registered project path contains the segment tiled-engine. With no custom projectDir mapping, Gradle expects the same-named child directory <Photos root>/tiled-engine. The underscore names a different directory.

Exercise 3 — After Lesson 1.1, can the project be called an Android library? Explain the missing fact.

Answer: No. It is a registered Gradle subproject. The Android library plugin has not been applied, so Android-specific configuration and Android build tasks do not exist yet. Lesson 1.2 adds that fact.

Exercise 4 — What single claim does a successful gradlew projects check support, and what tempting claim does it not support?

Answer: It supports the claim that :tiled-engine belongs to Gradle’s project hierarchy. It does not support the claim that the Android app or the future native engine builds.
