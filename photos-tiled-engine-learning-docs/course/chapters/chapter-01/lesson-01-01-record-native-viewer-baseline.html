Chapter 1 · Lesson 1.1 · Native viewer only

Record the isolated native-viewer baseline

Launch the standalone test activity. Observe the first frame that contains photo pixels. Then perform one short zoom-and-page sequence. This establishes the native viewer's visible starting point without changing Android code.

Scope for this lesson

  • Observe: the visible output and public callbacks of TiledImageView.
  • Exercise: first image content, refinement, one zoom action, and one page change.
  • Preserve: the current engine behavior as the comparison target for the rebuild.
  • Keep sealed: the implementation under tiled-engine/src/.
Why this entry point

The app already has an isolated engine test bench

NativeTestingActivity

This activity places one TiledImageView full-screen. It supplies three generated large photos directly. The third photo uses WebP. The first two use JPEG.

The generated coordinate grid makes a misplaced tile, wrong page, seam, or stale region easier to notice than an ordinary photo.

What this harness isolates

The activity supplies image files, a focused index, a viewport, and interaction events directly to the native viewer.

That keeps the observations tied to first-frame coverage, refinement, tile alignment, gestures, paging, formats, and surface lifecycle.

Launch and callback anchors

Two surviving host-side facts are enough for Lesson 1.1

Shell · direct launch
adb shell am start -n com.example.photos/.NativeTestingActivity

This opens the engine harness directly, with the first synthetic photo focused at index zero.

Kotlin · public host contract
// NativeTestingActivity.kt — abbreviated host calls
binding.tiledImage.setPhotos(files, 0)

override fun onReady() {
    Log.d(TAG, "First engine frame presented")
}

setPhotos supplies the gallery. onReady reports that a frame containing actual image content has reached the screen.

Do not measure launch latency in this lesson

The activity may generate its synthetic image files on the first run. That file-generation work happens before setPhotos. A launch-to-ready time from that run would mix test-data creation with engine startup.

Lesson 1.1 records visible behavior only. Controlled timing arrives later.

Vocabulary

Four terms used in the baseline

First image-content frameThe first presented screen frame that contains pixels from the focused photo. A black clear color alone does not qualify.
Fit scaleThe zoom scale that makes the complete logical photo fit inside the available viewport while preserving aspect ratio.
RefinementThe replacement or covering of coarser displayed image regions with higher-detail tiles while the intended photo framing stays the same.
Seam or stale tileA seam is an unintended visible line between neighboring tiles. A stale tile displays pixels from an older photo, region, zoom state, or request generation.
Interactive orientation

What to watch, in order

This stepper names observable states only. Later chapters will rebuild the internal work that produces each state.

1

Files supplied

The activity passes three generated image files and focuses index zero.

Inputs are the files and focused index.
2

First image content

The focused photo becomes visible at its initial fit framing.

This is the readiness boundary.
3

Initial refinement

Higher-detail visible regions may replace coarser coverage.

The intended framing should not jump.
4

Zoom interaction

A pinch or double tap changes scale and the visible logical image region.

Newly needed detail may refine afterward.
5

Page interaction

A horizontal swipe changes the focused photo inside the same surface.

The large page label proves which document is visible.

Exercises

Two quick checks

Exercise 1 — Does a successfully cleared black OpenGL frame satisfy onReady()?

Answer: No. A clear operation proves that the renderer can write a background color. The callback contract requires a presented frame containing actual pixels from the focused image.

Exercise 2 — Must the engine decode every source-resolution tile before the fit-scale photo can be ready?

Answer: No. The fit-scale viewport can be fully covered by a coarser pyramid level whose pixels are appropriate for that screen scale. Higher-detail tiles are needed only when the current zoom exposes more source detail.
