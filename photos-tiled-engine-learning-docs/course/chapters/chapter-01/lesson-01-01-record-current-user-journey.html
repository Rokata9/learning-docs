Where this lesson fits

Preserve behavior before reconstruction begins

A baseline is a recorded before-state. It gives the later rebuild something concrete to match. This lesson records user actions, visible frames, and logs. It does not explain the native engine's internal C++ implementation.

The principal idea is simple: an expectation from source code is not the same thing as a result observed on the device. Record both. Do not merge them.

This lesson changes

Learning-repository evidence only. You fill learner-work/observations/lesson-01-01-current-user-journey.md and add your own screenshots, recordings, and logs.

This lesson does not change

No Kotlin, C++, Java Native Interface (JNI), CMake, Gradle, XML, tests, or Android-project scripts. The complete tiled-engine/ directory remains present and sealed until Lesson 1.6.

Non-negotiable boundary

Do not inspect the native implementation

You may run the current app and inspect the surviving call sites in app/ and transition-framework/. Do not open files under tiled-engine/src/. The engine remains a black box in this lesson. A black box is a component whose inputs and outputs are observed while its internal implementation is deliberately hidden.

Also ignore the older learning chapters inside the Android project. This repository is the canonical course path.

Terms used in this lesson

Exact meanings

Baseline

A recorded before-state used for later comparison. Here it includes actions, visible outcomes, logs, environment, and anomalies.

Observable contract

The behavior a user or test can observe without knowing the internal implementation. Example: pressing Back on the entry photo morphs the image toward its grid cell.

Configured duration

A time value supplied to an animation or timer. It is not automatically the total time the user waits.

Measured latency

Elapsed time between two recorded events. Example: the time from the tap log to the native-ready log.

First live tiled frame

The first frame after TiledImageView reports readiness and the fragment hides the temporary detail ImageView. From that point, the visible image responds to the tiled viewer's gestures.

Plain back-stack pop

Removing the detail fragment without morphing a transition clone back into a grid cell.

The 75 ms timeout is not an extra fixed segment. It is a decision point inside the pre-transition wait. At 75 ms, the low-quality request may start. The low-quality drawable can become ready later.

Current debug configuration

The baseline is intentionally biased toward the low-quality transition drawable

The high-quality request asks Glide for a drawable near the destination view size. It is not the original file decoded byte-for-byte. Because the high-quality success callback is delayed by 2,000 ms while the fallback decision occurs after 75 ms, the low-quality path is the expected ordinary outcome in this attached baseline.

Source-proven expectation The timing constants and callback order are visible in source. Device evidence required Logcat must confirm which drawable actually won in your run.

Pressure-test the source

Three inconsistencies must remain explicit

Warm-up timing

The XML comment says the engine decodes while the shared-element animation runs. The current call order invokes loadFullResolutionImage() inside tfOnTransitionEnd. That is after the animation ends.

Course wording: the engine warms behind the destination placeholder after the clone animation.

Navigation documentation

tfNavigateToDestination says it uses an “add/hide” transaction. Its implementation calls add(...) and addToBackStack(...); it does not call hide(...).

Evidence limit: record the visible result. Do not claim the source fragment is hidden.

“Both return paths”

Only the entry-photo path performs a return animation. Paging or rotation performs a plain pop.

Course wording: one animated return outcome and two causes for the plain-exit outcome.

Preparation

Create a controlled but non-destructive baseline setup

Android project

  • Use the untouched project state that still contains tiled-engine/.
  • Record git rev-parse HEAD, git branch --show-current, and git status --short.
  • Do not clear application data. The app stores its captured photos in its internal files directory.
  • Build the current baseline before recording.
./gradlew :app:assembleDebug
# Install only when the device does not already have this exact build.
# Do not uninstall first; uninstalling would erase the app's stored photos.
./gradlew :app:installDebug

# PowerShell or cmd alternatives:
gradlew.bat :app:assembleDebug
gradlew.bat :app:installDebug

Device and photo set

  • Use the physical Pixel 8 Pro.
  • Enable normal device rotation for Run C.
  • Keep Android animation-scale settings unchanged and record their values.
  • Have at least three photos. Use a middle photo as the entry photo so paging can move in either direction.
  • Prefer one portrait, one landscape, and one high-detail photo.

Screen recording adds CPU, GPU, memory, and encoding work. Use it as visual evidence. Do not treat the recording's frame pacing as a performance measurement. Repeat the flows once without recording and write a separate subjective note.

Learner-authored evidence task

Run A — forward handoff, gestures, and animated return

A1. Start from a stable grid

  1. Force-stop and relaunch the app without clearing data.
  2. Choose a middle photo. Record its filename or a human-readable identifier in the worksheet.
  3. Capture the grid before tapping. The complete grid cell must be visible.

A2. Record the forward handoff

  1. Start the filtered Logcat capture shown below.
  2. Begin a short screen recording.
  3. Tap the selected grid photo once.
  4. Keep both hands off the screen until the Target: tile engine ready, swapping in surface log appears.
  5. Record whether the clone-to-placeholder and placeholder-to-surface boundaries show a flash, jump, scale mismatch, or color change.

A3. Exercise the live viewer

  1. Pinch in and out slowly. Watch one recognizable feature under the focal point.
  2. Pan in both axes while zoomed.
  3. Double-tap once.
  4. Perform one moderate fling.
  5. Record behavior only. Do not diagnose native internals in this lesson.

A4. Return while still on the entry photo

  1. Press Back without paging to another photo and without rotating.
  2. Record whether the image morphs toward the original grid cell.
  3. Confirm that the original grid thumbnail is visible and has normal opacity after the animation.
Learner-authored evidence task

Run B — page to a neighbor, then exit plainly

  1. Open the same middle entry photo and wait for the live tiled frame.
  2. Swipe horizontally until a neighboring photo becomes the current photo.
  3. Record the direction, final photo identifier, and whether the page snap is complete.
  4. Press Back.
  5. Confirm whether the detail fragment disappears without a morph animation.
  6. Confirm that the entry photo's original grid thumbnail is restored. Do not claim that the grid located the neighboring photo's cell; the current code does not implement that behavior.
Learner-authored evidence task

Run C — rotate, check framing, then exit plainly

  1. Open the entry photo and wait for the live tiled frame.
  2. Zoom and pan until the viewport has a recognizable off-center framing.
  3. Rotate to landscape. Wait for the detail view to become usable.
  4. Record whether the same logical photo area remains visible. “Logical photo area” means the same subject region after accounting for the new viewport shape.
  5. Rotate back to portrait and record the result again.
  6. Press Back. Confirm whether the screen pops plainly instead of running the return clone.

Source expectation A recreated fragment sets enteredViaTransition = false and bypasses the return animation. Device evidence required The surviving app comment says framing is restored, but the mechanism lives in the sealed viewer and must be observed rather than assumed.

Exercises

Answer in chat before opening the details

Exercise 1 — Does 300 ms mean tap-to-live latency?

Answer: No. The 300 ms value controls the overlay clone's Android transition after the transition drawable is ready and the start/end states have been configured. Tap-to-live latency also includes destination layout, transition-image acquisition, and the later setPhotos(...)-to-onReady() wait.

Exercise 2 — Diagnostic: what is visible immediately after the clone animation ends but before onReady()?

Answer: The destination fragment's transitionImage ImageView. The fragment copies the clone's drawable and matrix into it. The native view has View.VISIBLE, but its pixels are visually covered by the opaque destination ImageView. The surface is not yet the image-bearing object the user can see. The overlay clone is removed during transition cleanup.

Exercise 3 — What does the 75 ms timeout guarantee?

Answer: It guarantees neither a displayed low-quality drawable nor a 75 ms total wait. It only schedules the low-quality fallback request if the high-quality request is still considered in progress and no fallback is active when the timer fires.

Exercise 4 — What happens after paging to a neighbor and pressing Back?

Answer: The condition currentIndex != startIndex selects the plain-exit path. The framework state is reset, the grid receives a fragment result so it can restore the hidden entry thumbnail, and the back stack is popped. The neighboring photo does not morph into its own grid cell.
